# Auto Research Agent v1.1 实施规划

状态：**A–D 已完成；D 为 2026-09-20 增补的 local-process profile**

制定日期：2026-09-19

范围：A 证据与引用系统、B 长期研究记忆、C 自动实验迭代、D 第二研究场景与通用性验证

执行顺序：**A → B → C → D**，D 是 A–C 完成后的增补阶段。

## 1. 目标和版本规则

V1 已证明单条 AI 研究任务能够走通“证据 → 假设 → 计划审批 → 实验 → 分析 → 审查 → 审查响应 → 最终确认”。v1.1 的目标是将该原型升级为结构清晰、可维护、可扩展且经过检索和实验评测的科研系统。

本计划不以增加功能数量为优先目标。全局优先级固定为：

1. 研究严谨性和可追溯性；
2. 可恢复性、安全边界和数据完整性；
3. 自动化程度；
4. 运行速度；
5. 成本优化。

### 1.1 版本映射

| 阶段 | 版本 | 内容 | 发布条件 |
| --- | --- | --- | --- |
| 基线 | `v1.0.0` | 当前 V1、pi provider 配置和本规划 | 开始 A 前运行全部现有门禁并创建基线 tag |
| A | `v1.0.1` | 证据、全文、引用与成熟检索 worker | A 的数据迁移、评测和端到端验收全部通过 |
| B | `v1.0.2` | 可审计的跨 run 长期记忆 | B 的有/无记忆对照和删除测试全部通过 |
| C | `v1.0.3` | 有界自动实验搜索 | C 的泄漏检查、资源墙和搜索比较全部通过 |
| D | `v1.1.0` | CV 第二场景与核心通用性验证 | CV闭环到达done，通用性检查和本地profile门禁通过 |

每个阶段允许多个小型开发提交。阶段末创建一个 release commit 和 annotated Git tag。tag 前必须确保工作区干净、lockfile 固定、迁移可回滚、文档和测试结果已落盘。

开始 A 前先把 `package.json` 从原型版本 `0.1.0` 调整为 `1.0.0`，运行现有 V1 全部门禁，并在包含本计划的稳定基线上创建 `v1.0.0` annotated tag。后续 release commit 同步更新 package version。

原计划要求完成 `v1.0.3` 后重新评审 D。该评审已于2026-09-20完成，并通过第14节增补确定 Digits CV 案例与 `v1.1.0` 验收。

### 1.2 本计划的非目标

- Web UI、多用户和云端 SaaS；
- 微服务、消息队列和 Kubernetes；
- 自动生成可投稿论文；
- 湿实验或受试者研究的自动执行；
- 以向量数据库或模型摘要替代事实数据库；
- 为追求 SOTA 自研检索算法。

## 2. 跨阶段架构

### 2.1 模块化单体

采用模块化单体和 ports/adapters。TypeScript 是控制平面，Python worker 和文档解析器是受控数据平面。

```text
CLI
 └─ application/use-cases
     ├─ research workflow
     ├─ evidence ingestion/retrieval
     ├─ memory promotion/retrieval
     └─ experiment search/scheduling
          │
          ├─ domain
          │   ├─ evidence graph
          │   ├─ memory lifecycle
          │   └─ experiment search graph
          │
          └─ ports
              ├─ LedgerPort
              ├─ ArtifactStorePort
              ├─ RetrievalPort
              ├─ ModelPort
              ├─ ExperimentRunnerPort
              └─ SchedulerPort

infrastructure/adapters
 ├─ SQLite ledger + FTS5
 ├─ content-addressed artifact store
 ├─ pi ModelRuntime
```

核心 domain 和 application 层不得 import pi、SQLite、PaperQA2、GROBID、Docling、Docker 或特定数据集 SDK。外部组件通过版本化 port 接口接入。

## 3. 配置、预算与运行策略

### 3.1 配置优先级

配置优先级固定为：

```text
内置安全默认值 < 项目 YAML < ResearchBrief < CLI 临时覆盖
```

- YAML 必须通过 JSON Schema 和运行时 schema 双重校验；未知字段默认报错。
- 使用固定版本的 `yaml` 解析器；Zod是配置的规范运行时 schema，并从同一 schema 生成 JSON Schema，禁止维护两份手写规则。
- secret 只从环境变量、pi auth 或外部 secret command 获取，不得出现在 YAML、brief、SQLite 事件或日志中。
- CLI 输出合并后的非敏感 effective config，并记录配置哈希。
- ResearchBrief 可以调低硬上限；调高需要审批记录，不能只靠配置覆盖。
- 每一阶段保存 config schema version，配置升级提供 migration 或清晰报错。

### 3.2 默认资源墙

所有数值均可配置，但以下为项目默认值：

| 资源 | 软阈值 | 硬上限 |
| --- | ---: | ---: |
| 单 run 模型费用 | 8 USD | 10 USD |
| 总墙钟时间 | 20 h | 24 h |
| GPU 时间 | 20 GPU-hours | 24 GPU-hours |
| 候选实验数 | 16 | 20 |
| 并发实验数 | 1 | 2 |
| 单模型调用 | 90 s | 120 s |
| 单检索请求 | 30 s | 60 s |
| 单全文解析 | 3 min | 5 min |

费用价格表必须带 provider、模型、币种、单位、有效日期和来源。价格未知时，金额只作 `unknown`，同时用请求数、token 和时间硬限制，不能假装费用为零。

软阈值产生事件和提示；硬上限立即停止新工作、取消可取消任务、保存已完成产物并写明停止原因。运行时间墙、GPU 墙和模型墙分别计算。

### 3.3 可观测性

- 使用 OpenTelemetry 语义记录本地 spans，但默认不向外发送 telemetry。
- 每个外部调用记录 operation、provider、deadline、重试、状态、延迟、token/费用和经过脱敏的输入哈希。
- 每个检索调用记录查询、过滤条件、索引版本、各阶段分数和最终排名。
- 每个实验记录资源用量、退出状态、失败分类和产物。
- 人类审批记录创建时间、响应时间、决策和修改内容。
- 日志为结构化 JSONL；用户报告从账本生成，不反向解析日志作为事实。

## 4. 数据、迁移和文件系统

### 4.1 SQLite 事实库

V1.1 继续使用 SQLite，启用 WAL、foreign keys 和显式事务。SQLite 是唯一事实源。向量、Tantivy 和模型缓存均是可删除重建的派生索引。

数据库至少包含以下逻辑组：

```text
system
  schema_migrations, config_snapshots, background_jobs
research
  runs, records, events, decisions, model_calls, budget_events
evidence
  sources, source_identifiers, document_versions, passages,
  claims, claim_evidence, citation_edges, search_queries,
  search_results, retrieval_events, parser_runs
memory
  namespaces, memory_items, memory_relations, memory_sources,
  memory_promotions, memory_access_log, memory_jobs
experiments
  search_runs, experiment_nodes, experiment_edges, patches,
  metric_observations, resource_usage, retry_attempts
artifacts
  artifacts, artifact_links, manifests
```

所有多表状态转换必须在事务内完成。外部文件先写临时文件、校验并原子 rename，再在事务中登记；不得在数据库中指向未完成文件。

### 4.2 Migration 规则

- 使用单调递增 schema version 和不可变 migration 文件。
- 升级前自动创建 SQLite backup 和 artifact manifest snapshot。
- migration 在真实 V1 数据副本、空数据库和部分失败数据库上测试。
- 旧 run 保持可读；若新字段无法推导，使用明确的 `unknown`，不能编造默认事实。
- 每次 release 提供 migrate、verify 和 rollback 文档。
- 数据库版本高于程序支持版本时拒绝启动。

### 4.3 内容寻址文件库

路径由 SHA-256 决定，数据库保存媒体类型、长度、许可、来源 URL、获取时间和逻辑用途。原始文件、解析结果和派生结果分别登记，处理过程永不覆盖原始文件。

```text
artifacts/sha256/ab/cd/<full-hash>
```

备份必须同时包含 SQLite snapshot 和 artifact manifest。启动和验收时执行完整性抽查；引用缺失文件时标记 broken provenance。

## 5. A 阶段：证据与引用系统（v1.0.1）

### 5.1 目标

将元数据和摘要级记录升级为可定位到正文 Passage 的证据系统。关键主张必须回溯到合法获取的正文、官方代码或可重跑实验。

### 5.2 复用组件

默认采用以下成熟组件，不自行实现全文索引和向量数据库：

| 组件 | 用途 | 集成方式 |
| --- | --- | --- |
| PaperQA2 `v2026.08.12` / commit `57e89f7223b0960d5ee5ea048c69e3c47e088572` | 论文搜索、Tantivy索引、chunk embedding、evidence gathering、重排和 benchmark | 独立 Python worker；Apache-2.0；固定版本与 hash |
| GROBID | 学术 PDF → TEI、章节、引用和版面定位 | 固定 Docker image digest；主 PDF parser |
| Docling | 扫描 PDF、复杂表格和 OCR fallback | Python worker 可选 extra；固定模型和版本 |
| BGE-M3 | 默认本地 embedding | 固定 Hugging Face revision、维度与归一化配置 |
| Qdrant | 大于内存时的可选 vector backend | 不作为 v1.0.1 默认；实现 adapter contract 即可 |
| Feynman commit `dfdcb7cf2c73183cff7b10aa8ea8ce370c8b152c` | provenance sidecar、OpenAlex citation graph、可解释 PaperRank 的设计参考 | MIT；借鉴接口，非运行依赖 |
| STORM commit `fb951af7744dab086e34962e9bc6fe878e145f83` | 本地/远程 Qdrant 与 BGE-M3 配置参考 | MIT；设计参考 |

依赖必须生成 SBOM。复制或改写上游代码时保留许可证与归属；优先通过公开 API 和 adapter 复用，禁止复制整个外部 agent 框架。

### 5.3 Python worker

位置为 `workers/retrieval/`，Python >=3.11，使用 uv 和 `uv.lock`。Node 管理一个长驻子进程，使用 JSONL RPC over stdio：

```text
Request:  {schemaVersion, requestId, method, params, deadlineMs, idempotencyKey?}
Response: {schemaVersion, requestId, ok, result?, error?, metrics}
Event:    {schemaVersion, requestId, event, progress}
Cancel:   {schemaVersion, requestId, method:"cancel"}
```

- 读操作在 worker 崩溃后最多自动重试一次。
- ingestion 写操作只有带 idempotency key 才允许恢复，禁止盲目重复。
- stdout 仅传协议；日志写 stderr。
- 响应通过共享 JSON Schema 验证。
- worker 版本、Python、PaperQA2和模型 revision 在 handshake 中返回。
- 远程 HTTP backend 只保留接口，不在本阶段实现。

### 5.4 元数据规范化

字段级来源优先级如下：

- DOI 注册元数据：Crossref/DataCite；
- arXiv ID、版本和提交时间：arXiv；
- 作者机构、引用关系和 OA location：OpenAlex；
- 摘要、推荐和补充引用：Semantic Scholar；
- 官方项目页和一般网页：AnySearch；
- 用户提供的合法文件：保留用户来源，不覆盖注册元数据。

规范化标识符包括 DOI、arXiv ID、OpenAlex ID、Semantic Scholar ID、PMID/PMCID、URL canonical form。合并是字段级操作，每个最终字段保存来源、获取时间和原始响应 artifact。冲突不静默覆盖。

### 5.5 全文获取与解析

获取优先级：结构化 HTML/XML → GROBID PDF → Docling/OCR fallback → 摘要级降级。

自动保存范围仅限合法公开全文。付费墙、登录或禁止再分发的材料不绕过访问控制；只记录元数据、摘要、访问限制和用户本地合法文件引用。原始文件不提交 Git。

统一中间模型 `CanonicalDocument` 必须包含：

- document/version ID、规范标识符和来源；
- 标题、作者、摘要；
- section 层级；
- paragraph、table、figure、caption、formula note、reference；
- 页码、字符范围和可用时的 bounding box；
- 原文件 hash、parser、parser version、配置 hash；
- 解析警告和质量指标。

各 parser 只能输出 `CanonicalDocument`。PaperQA2接收从该模型生成的 texts/chunks，parser 内部对象不能进入 domain 数据库。

### 5.6 Passage 与 chunk

- Passage 是证据定位单位；优先遵循 section/paragraph 边界。
- 过长段落按 token 切分；表格、caption 和 reference 独立处理。
- 保存 parent section、前后相邻 Passage 和原始定位。
- chunk token size、overlap、table policy 都是配置参数，通过 benchmark 选择默认值。
- 索引版本键为：

```text
source_hash + parser_version + parser_config_hash
+ chunk_config_hash + embedding_model_revision
```

新索引在临时目录完成构建、计数和抽样验证后原子切换 active pointer。旧 Claim 继续指向旧 Passage，不自动重绑。

### 5.7 Claim 与证据门禁

Claim 类型和要求：

| Claim 类型 | 最低证据要求 | 缺失时行为 |
| --- | --- | --- |
| 核心贡献、数值结果、已有工作比较 | 正文 Passage 或可重跑实验 | 阻止最终报告 |
| 方法、数据集、实现事实 | 正文、官方文档或代码定位 | 阻止最终报告 |
| 综合推断 | 至少两个证据单元，明确标记 inference | 降级或阻止，取决于报告重要性 |
| 假设和未来工作 | 可无支持证据，但标记 unverified | 允许 |

关系类型至少包括 `supports`、`refutes`、`background`、`uncertain`。摘要只支持摘要明确陈述的内容。contextual summary 是检索候选，不能取代原文 Passage。

### 5.8 检索接口

Agent 只使用原子工具，不使用“自动给结论”的黑盒 RAG：

- `search_metadata`
- `search_passages`
- `lookup_identifier`
- `expand_citations`
- `fetch_document`
- `get_passage`
- `explain_retrieval`

PaperQA2负责候选论文、Tantivy全文检索、embedding召回、contextual summary 和候选重排。SQLite FTS5用于 metadata、Claim、Memory 的确定性查询和应急 fallback。默认小规模 vector store 使用 PaperQA2的 NumPy实现；达到配置阈值后才评估 Qdrant。v1.0.1 不引入 LanceDB、LlamaIndex或Haystack作为核心依赖。

检索停止条件：至少执行问题、方法签名和相邻领域三组查询；记录数据库、时间窗口和结果数；连续两轮没有新的高相关工作且关键引用链已覆盖才允许宣布饱和。预算先耗尽则结束为 `coverage_incomplete`。

### 5.9 模型职责

- 主研究 agent 通过 pi 运行。
- PaperQA2 worker 允许通过 LiteLLM 使用独立 `evidence_model`，保留其经过验证的 contextual summarization/re-ranking路径。
- 默认 evidence model 选择便宜模型；provider、model、token、费用和用途写入统一预算账本。
- 默认 embedding 是固定 revision 的本地 BGE-M3；远程 embedding 是可配置 backend。
- evidence model 或 embedding 不可用时按 5.10 降级。

### 5.10 降级和硬失败

| 故障 | 行为 |
| --- | --- |
| embedding 不可用 | Tantivy/关键词检索 |
| evidence model 不可用 | 返回未重排 passages，标记 semantic review missing |
| 全文不可得 | 摘要级证据，限制可支持 Claim 范围 |
| 单个元数据源失败 | 缓存和其他来源，记录 coverage gap |
| parser 失败 | 尝试下一 parser；全部失败则摘要降级 |
| 原始文件 hash 失败 | 硬停止 |
| Passage locator 丢失 | 硬停止证据晋升 |
| SQLite 事务失败 | 硬停止 |

任何降级写入运行报告。发生影响核心 Claim 的降级时，不得宣称完成完整证据核查。

### 5.11 A 阶段任务顺序

1. 创建架构 ADR、目录骨架、配置 schema 和 migration runner。
2. 将现有 Ledger、pi adapter 和 CLI 移入 ports/adapters，保持行为不变。
3. 建立内容寻址文件库和 evidence schema migration。
4. 建立 Python worker、handshake、deadline、cancel、restart 和 idempotency。
5. 固定 PaperQA2/uv lock/SBOM，跑通上游 smoke test。
6. 实现 metadata clients 和原始响应快照。
7. 实现 CanonicalDocument、GROBID 主 parser 和 Docling fallback。
8. 实现 Passage/Claim/ClaimEvidence 与报告门禁。
9. 暴露七个检索工具并接入 pi。
10. 建立 benchmark、运行基线与混合检索对照。
11. 迁移 V1 数据副本，跑完整科研流程回归。
12. 编写 release report、创建 `v1.0.1` tag。

### 5.12 A 阶段验收

公共评测使用 PaperQA2的 LitQA2/LFRQA 固定子集；项目评测至少 40 个查询，覆盖精确论文、方法别名、相邻工作、反证、数据集和官方代码。

最低门禁：

- exact identifier lookup：100%；
- 项目集关键论文 Recall@20：≥ 0.90；
- 项目集 nDCG@10：≥ 0.70；
- Passage locator/hash 完整率：100%；
- 人工标注核心 Claim 的 citation support precision：≥ 0.90；
- 相对直接调用相同版本 PaperQA2，固定公共子集的主要指标不得下降超过 5%；
- warm local retrieval P95：≤ 2 s，不含首次 embedding/ingestion；
- 错误引用、损坏 hash 和 locator 丢失门禁测试全部通过；
- 所有查询可解释并包含索引版本与分数；
- V1 fastText run 迁移后仍可读取和生成报告。

若混合检索没有稳定优于关键词基线，则关键词保持默认，混合模式标为 experimental；不得为了按期发布而降低评测阈值。

## 6. B 阶段：长期研究记忆（v1.0.2）

### 6.1 目标

让后续任务复用已验证的来源、实验、失败和决策，同时保证每条记忆可追溯、可冲突、可失效、可纠正和可删除。

### 6.2 可进入记忆的对象

- 已核验 Source、Passage 和 Claim；
- 已执行 ExperimentPlan/ExperimentRun/Finding；
- 已审批 Decision；
- 可复用 Procedure；
- 明确标记未验证的 Hypothesis；
- 负结果、失败原因和无效配置。

聊天记录、compaction摘要和模型自由文本只保留在 run log，不能直接晋升。每条记忆必须有 source run、证据引用、创建者、模型/工具版本、适用范围和状态。

### 6.3 生命周期

```text
candidate → reviewed → verified → superseded | retracted | archived
```

- agent 只能自动创建 candidate。
- run 完成独立审查和最终人工确认后，promotion job 才能晋升 verified。
- 未验证记忆默认不得影响高风险决策。
- 负结果与失败经验遵循相同晋升规则。
- 状态转换追加事件，不覆盖历史。

### 6.4 Namespace

| Scope | 默认可见性 |
| --- | --- |
| run | 当前 run |
| project | 同一研究项目 |
| workspace | 本地全部项目，需任务允许 |
| global | 显式导入的公开知识/通用方法 |

默认检索 `run + project`。扩大到 workspace/global 必须在 brief 中显式允许，并在 MemoryCard显示 scope。私有项目禁止自动向外层晋升。

### 6.5 冲突与时效

新 Claim 不覆盖旧 Claim，使用 `supports`、`refutes`、`supersedes` 关系。存在未解决冲突时同时返回双方证据。

- API、软件版本、数据集版本、SOTA 等对象设置 `revalidate_after`；
- 固定实验记录和理论证明不因时间自动降权；
- 过期只影响检索与决策等级，不删除记录；
- revalidation 创建新版本和关系。

### 6.6 记忆检索

1. namespace、对象类型、验证状态、领域、日期、软件/数据版本做结构化过滤；
2. SQLite FTS5 与可选 embedding 做召回；
3. provenance、验证等级、冲突状态和任务相关性重排；
4. 正面结果、负结果和反证分别保留召回 quota；
5. 返回少量结构化 MemoryCard。

向量相似度不能绕过 scope 或 verification filter。embedding索引仍是派生物，版本规则沿用 A。

### 6.7 MemoryCard

```text
id, type, content, status, namespace,
sourceRun, claim/passages/experiment refs,
supportingEvidence, opposingEvidence,
applicability, invalidationConditions,
revalidateAfter, retrievalReason,
scores, tokenCost
```

每个工作流阶段配置 memory token budget。超出预算按相关性和证据等级裁剪；不得生成无来源摘要压缩事实。agent 可以调用 `inspect_memory` 查看完整 lineage。

### 6.8 去重、整理和任务

- 标识符、内容 hash、规范化配置或实验签名完全相同可自动合并引用。
- 语义相似只创建 `possible_duplicate`。
- consolidation 生成新 memory，原条目不删除。
- run 期间只写 candidate；promotion、冲突检测、去重和 consolidation 在 run 完成后作为后台 job。
- job 可暂停、取消、重试，有独立预算，不阻塞原始证据和实验落盘。

### 6.9 用户控制

CLI 必须实现：

```text
memory list/search/show/trace
memory correct/retract/archive/purge
memory export/import
memory jobs
```

- correction 创建新版本，并将旧版本 supersede/retract；
- archive 可恢复且默认不召回；
- retract 保留审计但禁止作为有效依据；
- purge 删除正文、embedding、缓存和未共享产物，生成不含原内容的删除证明；
- 引用被 purge 对象的记忆转为 broken provenance，禁止晋升；
- Git 历史中的公开提交不承诺自动擦除。

1. memory schema、namespace policy 和 migration。
2. candidate writer 与 verified promotion job。
3. structured/lexical/semantic retrieval 和 MemoryCard。
4. memory tools 接入 pi，并实施每阶段 token budget。
5. conflict、revalidation、duplicate 和 consolidation。
6. CLI 检查、纠错、归档、删除、导入导出。
7. 构造三任务连续研究 benchmark。
8. 运行有记忆/无记忆 A/B 对照。
9. 数据迁移、备份、purge 和恢复演练。
10. release report 和 `v1.0.2` tag。

### 6.11 B 阶段验收

至少使用三个连续且相关的研究任务，对相同模型、相同预算进行有记忆/无记忆对照。

- verified MemoryCard provenance完整率：100%；
- candidate 影响关键决策：0 次；
- 跨 namespace 未授权召回：0 次；
- 已 retract/purge 记忆作为有效证据召回：0 次；
- 正确复用的配置/证据有可核查增量；
- 重复检索或重复实验至少减少 30%，否则 B 的收益判为未证明；
- 模型 token 或总费用不得恶化超过 10%，除非结论质量有预先定义的显著提升；
- 错误/过期记忆引用不得高于无记忆基线，核心事实错误为 0；
- correction、conflict、archive、purge、export/import 和恢复测试全部通过；
- 报告研究者审阅时间和最终质量，而不只报告召回数量。

若收益门禁未通过，memory保留为 opt-in，不默认启用；不得通过放宽事实错误标准发布。

## 7. C 阶段：自动实验迭代（v1.0.3）

### 7.1 目标

在一次批准的搜索空间和资源预算内，自动提出、实现、运行、比较和淘汰候选，并保留完整搜索树、失败与负结果。

### 7.2 搜索策略

实现统一 `SearchStrategyPort`：

- `linear`：相同预算下的基线；
- `best-first`：v1.0.3目标策略。

每个节点是一项完整候选实验。best-first只扩展当前最高优先级的少量节点。优先级由批准的验证指标、稳定性、失败风险、成本和复杂度组成。debug child 与 novel candidate 分开计数。

暂不实现多 agent 协商和贝叶斯优化。将来可通过 port 增加，但不能改变节点、预算和审计契约。

### 7.3 修改模式

`parameter mode` 只能修改声明的参数空间。`patch mode` 允许修改批准目录，并限制：

- allowlist路径和文件类型；
- 最大文件数、行数和 diff bytes；
- 禁止修改 evaluation、sealed data、scheduler、sandbox 和审计代码；
- 禁止依赖变化；
- patch 必须应用到独立 workspace，并经过静态检查。

新增依赖、数据源、权限、网络或预算必须暂停并重新审批。

### 7.4 数据角色与泄漏防护

数据 manifest 固定四种角色：train、validation、test、audit。

- train用于拟合；
- validation用于候选排序和停止；
- test在候选冻结和人工批准后只运行一次；
- audit可选，用于最终复核。

搜索容器只挂载 train/validation。test artifact在搜索完成前不可见，路径和密钥不进入提示或环境。观察 test 后不得返回同一 run 的搜索阶段；继续研究必须创建新 run 并标记 `prior_test_observed=true`。

### 7.5 模型角色

- planner：提出候选和预期影响，只读证据与搜索状态；
- coder：生成参数变更或受限 patch；
- evaluator：读取验证结果，不能写代码；
- reviewer：搜索结束后审查选择偏差、失败和最终 test 计划。

角色拥有独立 prompt、schema、工具 allowlist 和预算。可以配置相同模型，但权限不能合并。evaluator不可访问 test。

### 7.6 执行与调度

默认使用无网络 Docker：

- 基线代码、数据和共享 cache 只读挂载；
- 每个节点独立可写 workspace；
- image 使用 digest；
- 明确 CPU、RAM、GPU、PID、磁盘和 timeout；
- GPU 使用租约、设备锁和 heartbeat；
- 异常退出回收 GPU 和子进程；
- scheduler先支持本机队列，保留 Slurm/远程 port。

可信、固定 hash 的准备阶段可以申请联网。候选实验不得联网。

### 7.7 节点签名和复现

每个节点保存：parent、Git commit/patch、image digest、data manifest、配置、种子、命令、环境白名单、日志、指标、资源、生成模型、prompt hash、token、失败分类和重试记录。

节点签名由所有会影响结果的输入计算。相同签名直接复用完成结果。复用记录必须指向原节点，不能复制成新的独立实验。

### 7.8 统计设计

两阶段：

1. screening：所有候选使用少量固定配对种子；
2. confirmation：少数候选使用预留、此前不可见的新种子。

最终报告效应量、分布和不确定性。若使用顺序检验或提前停止，规则必须在搜索前写入计划。固定测试集上的重复训练种子不视为独立数据集。

### 7.9 排名与停止

多目标规则包括首要验证指标、跨种子稳定性、失败率、时间/GPU/模型费用、复杂度/模型大小和最小实际改进阈值。

任一条件触发停止：

- 任何硬预算耗尽；
- 配置的连续无实际改进次数达到上限；
- 全部可扩展候选失败；
- 预设统计判据已满足；
- 安全、权限或数据边界违规。

不得因单个种子最高分宣称成功。

### 7.10 失败与重试

| 类型 | 策略 |
| --- | --- |
| 基础设施瞬时错误 | 相同节点最多一次重试 |
| 确定性代码错误 | 允许有限 debug child |
| 资源超限 | 失败，不自动扩大资源 |
| 指标缺失/数据异常 | 硬失败并审查 |
| 安全/权限/数据违规 | 停止整个 run |

重试和调试计入预算；原始日志不可覆盖。

### 7.11 依赖与缓存

搜索前生成批准 lockfile 和基础 image。搜索期间断网，只使用镜像内依赖。新增依赖需独立准备阶段检查许可证、固定版本和 image digest。数据、模型和编译 cache按内容 hash只读挂载。

### 7.12 人工门

1. 搜索前审批问题、修改范围、指标、数据角色、统计规则和总预算；
2. 计划外依赖、数据、权限、网络和预算变更时暂停；
3. 搜索结束后审阅完整树、最佳候选、失败与 test 计划，再批准一次最终 test；
4. test 后审阅结论和限制，完成 run。

批准的 validation 搜索空间内不逐节点确认。

### 7.13 完整报告

必须包含总候选数、成功/失败数、全部节点指标与成本、选择和淘汰理由、多重尝试数、验证分布、confirmation、最终 test、负结果和人工干预。最高 validation 分数不能作为无偏 test 估计。

### 7.14 C 阶段验收任务

使用现有 fastText/AG News 场景建立自动搜索验收，不引入第二研究领域：

- 从公开训练集确定性、分层切分 train/validation；
- published test保持 sealed；
- 搜索批准的 `lr`、`dim`、`wordNgrams`、`epoch` 等有限参数；
- parameter mode为主，加入一个受限 patch mode smoke case；
- linear 与 best-first使用相同候选数、种子和总预算；
- 搜索结束后仅最佳冻结候选获批运行一次 test。

### 7.15 C 阶段任务顺序

1. search graph schema、migration、node signature 和 artifact关系。
2. data-role manifest 和 sealed test执行隔离。
3. parameter/patch mode、静态校验和独立 workspace。
4. Docker runner、GPU scheduler、资源 telemetry 和回收。
5. planner/coder/evaluator/reviewer权限与 schema。
6. linear strategy。
7. bounded best-first strategy。
8. screening/confirmation 和停止策略。
9. 完整搜索报告和人工门。
10. fastText验收任务和线性/树搜索对照。
11. 故障注入、泄漏测试和资源墙测试。
12. release report 和 `v1.0.3` tag。

### 7.16 C 阶段验收

- test在批准前被搜索进程读取：0 次；
- 越权路径、网络、依赖和预算操作成功：0 次；
- 每个节点复现信息和 lineage完整率：100%；
- 相同节点签名重复执行：0 次，必须命中复用；
- 硬预算超支：0；
- 注入崩溃后 GPU、进程和 workspace回收测试通过；
- 失败、重试、debug child和负结果全部进入报告；
- 相同预算下运行 linear 与 best-first 多次配对比较；best-first的 median best validation score 不低于 linear，并至少在一项预先定义的效率或质量指标上更好，否则 best-first保持 experimental；
- 最终 test只运行一次，结果不反馈到同一搜索树；

## 8. 跨阶段测试矩阵

每个 release 必须通过：

- unit：domain规则、schema、预算、排序和状态转换；
- contract：port和JSONL RPC schema；
- migration：空库、V1副本、前一版本和失败恢复；
- integration：SQLite、artifact store、worker、parser、pi和Docker；
- golden：固定文献、Passage、Claim和报告；
- failure injection：worker crash、timeout、网络失败、损坏文件、磁盘不足和进程泄漏；
- security：secret扫描、路径穿越、命令参数、恶意PDF/HTML、prompt injection和权限边界；
- performance：ingestion、warm retrieval、memory query和scheduler；
- end-to-end：真实但低成本的公开任务。

测试夹具不得依赖随时变化的远程结果；外部 API 使用录制响应或本地 fixture，另设显式联网 smoke test。

## 9. 安全与不可信内容

- 网页、PDF、代码库和模型输出均是不可信数据，不得作为系统指令执行。
- parser运行在受限容器或 worker，设置文件大小、页数、CPU、内存和时间限制。
- 下载校验媒体类型、重定向、允许协议和最大尺寸。
- 实验命令使用参数数组，不拼接 shell；secret-like环境变量默认拒绝进入实验。
- 报告引用的摘录遵守许可和合理长度，不把受限全文复制到 Git。
- purge覆盖派生索引、cache和artifact引用；备份按保留策略处理。

## 10. 性能策略

- 先 profile，再优化；每项性能修改附 benchmark。
- ingestion按document hash去重，embedding按model revision + chunk hash缓存。
- metadata请求批处理，遵守provider rate limit并采用有界退避。
- SQLite写事务短小，批量插入；长解析不持有写锁。
- worker长驻以避免Python冷启动；模型懒加载并报告首次加载成本。
- 并行只用于独立任务；所有并发受配置 semaphore限制。
- 不为当前规模引入PostgreSQL、微服务或分布式队列。

## 12. Luna Max 执行规则

后续执行模型应遵循以下顺序：

1. 读取 README、V1总结、本计划和当前Git状态；
2. 为当前阶段建立 checklist，并确认前一阶段tag存在；
3. 先完成迁移、port和测试夹具，再接外部依赖；
4. 每次提交保持可构建、可迁移、可回滚；
5. 不提前实现下一阶段；
6. 遇到外部组件与假设不符时，完成兼容性证据和 ADR，不用临时代码绕过；
7. 跑完阶段所有门禁，生成 release report；
8. 只有验收完全通过才创建 release commit和tag。

禁止为了“完成阶段”而降低引用、泄漏、安全、预算或事实错误门禁。负结果意味着保留当前默认实现并记录未证明收益，不意味着伪造成功。

## 14. D 阶段增补决策（v1.1.0）

增补日期：2026-09-20。A–C 完成后，D 选择 scikit-learn Digits 图像分类的一像素平移增强消融。选择依据是它与 AG News 的输入模态和预处理明显不同，同时数据公开内置、CPU 成本低、能固定依赖和完整重放。
