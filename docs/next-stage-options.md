# 下一阶段备选方案

日期：2026-09-19

决策状态：已选择按 A → B → C 顺序实施，完整要求见 [v1.1 实施规划](v1.1-plan.md)。D 延期到前三阶段完成后重新规划；E 不作为独立阶段，其 provider配置和成本墙作为横向基础设施持续维护。

V1 已完成单条 AI 研究任务的可追溯闭环。下一阶段应选择一个主目标，完成验收后再进入其他路线，避免同时扩展检索、记忆、实验搜索和交互界面而无法判断哪项改动真正有效。

## 快速比较

| 方案 | 主要解决的问题 | 对科研质量的近期收益 | 工程量 | 主要风险 |
| --- | --- | ---: | ---: | --- |
| A. 证据与引用系统 | 搜索噪声、缺少全文和精确出处 | 高 | 中 | 全文获取和许可差异 |
| B. 长期研究记忆 | 不同任务不能复用已验证经验 | 中高 | 中高 | 把错误结论长期保存并传播 |
| C. 自动实验迭代 | 当前只能执行一组预先给定对照 | 高 | 高 | 算力失控、测试集泄漏、搜索偏差 |
| D. 第二场景与通用性 | 目前只验证了文本分类 | 中 | 中 | 过早抽象、场景选择不具代表性 |
| E. 本地模型与成本控制 | 依赖远程 API，缺少金额预算 | 中 | 中 | 本地模型科研判断质量不足 |

## 方案 A：证据与引用系统（推荐）

### 目标

把当前的“论文元数据与摘要列表”升级为能支撑科研结论的证据库。每条关键主张应关联论文正文中的章节、页码或段落，并标明证据支持、反驳或仅提供背景。

### 工作内容

1. 建立 DOI、arXiv ID、标题和版本的规范化与去重规则。
2. 接入合法可得的 HTML/PDF 全文，保存访问时间、内容哈希和许可状态。
3. 将 `Source → Passage → Claim` 建成结构化关系；区分直接证据、间接证据和模型推断。
4. 增加检索相关性重排、搜索覆盖说明和低相关结果过滤。
5. 在报告生成前自动检查引用是否存在、是否能定位、是否支持对应主张。
6. 用 fastText 案例和另一个小型文献问题建立回归评测集。

### 交付物与验收

- 全文获取与解析适配器、证据表和数据库迁移。
- 报告中的关键文献主张能够跳转到具体段落或页码。
- 构造的错误引用、失效链接和“来源存在但不支持主张”都能被门禁拦截。
- 搜索结果保留查询边界，并能解释纳入和排除原因。
- 对无法获得全文的论文明确降级为摘要级证据。

### 选择条件

如果下一步希望提高研究报告可信度、选题核查质量和后续记忆质量，应选择此方案。完成后再做方案 B，可以避免把来源不明的摘要长期保存。

## 方案 B：长期研究记忆

### 目标

让新任务能够检索以往项目中已验证的来源、实验、失败模式和决策，同时保证记忆有来源、可失效、可纠正。

### 工作内容

1. 将记忆分为来源记忆、实验记忆、决策记忆和经验规则，禁止直接保存无来源的自由文本结论。
2. 建立跨 run 检索接口，先使用 SQLite 全文索引和结构化过滤；有明确收益后再增加向量检索。
3. 为记忆保存来源 run、生成模型、证据 ID、置信度、创建时间和失效条件。
4. 新证据冲突时保留版本和反证关系，不静默覆盖旧记录。
5. 在模型上下文中记录记忆为何被召回，并限制注入数量和 token 预算。
6. 增加遗忘、归档、人工更正和项目隔离机制。

### 交付物与验收

- `memory search/show/correct/archive` CLI 与可审计的记忆表。
- 第二个研究任务能复用第一个任务的有效配置或失败经验，并显示出处。
- 过期、冲突和低置信度记忆不会被当作确定事实。
- 有记忆与无记忆运行的比较，至少测量重复检索量、模型调用量和错误引用数。

### 选择条件

如果近期会连续开展多个相关 AI 研究任务，并希望减少重复检索和重复踩坑，可选择此方案。当前证据层仍以摘要为主，因此首版记忆必须严格限制为有明确 provenance 的内容。

## 方案 C：自动实验迭代

### 目标

让 agent 在批准的搜索空间和预算内提出多个候选修改，根据验证集结果选择、修复或停止，而不需要研究者逐次下达命令。

### 工作内容

1. 增加候选、父子关系、搜索分支和失败原因的数据结构。
2. 将数据严格分为训练、验证和最终测试；搜索过程不得读取测试指标。
3. 支持线性策略和小规模 best-first 策略，并设置分支数、调试次数和无进展停止条件。
4. 每个候选保存代码 diff、环境、资源成本、指标和淘汰原因。
5. 增加并发资源调度、GPU/CPU 配额和异常进程清理。
6. 用一个低成本 ML 任务比较固定方案、线性迭代和树搜索。

### 交付物与验收

- 在一次批准后自主完成多个候选实验，并严格停在预算内。
- 测试集在候选选择完成前不可见；日志能够证明无泄漏。
- 失败分支、负结果和被淘汰方案全部保留。
- 相同预算下能比较不同搜索策略，而不是只展示最好结果。

### 选择条件

如果主要目标是尽快提升 agent 的实验自主性和探索能力，可选择此方案。它对算力管理和评估设计要求最高。

## 方案 D：第二场景与通用性验证

### 目标

选择一个与文本分类性质明显不同的研究案例，检验现有核心契约是否真正通用，并修复被 fastText 案例掩盖的领域耦合。

### 候选场景

- 小规模计算机视觉消融实验，例如数据增强或正则化对公开小数据集的影响。
- LLM 推理或检索增强方法检查，使用固定公开评测集和本地小模型。
- 不自动执行的外部实验场景，验证 `awaiting_external_result` 和结果导入流程。

### 工作内容

1. 先写场景契约和验收指标，再选择论文、代码和公开数据。
2. 不复制 fastText 专用逻辑，通过 adapter 接入数据、指标和实验环境。
3. 比较两个场景需要修改的核心代码，发现通用性问题时优先修正接口。
4. 验证 Docker 隔离路径，而非继续使用可信进程模式。

### 交付物与验收

- 第二个真实任务运行到 `done`，包括审查和负结果保留。
- `core` 不包含领域、数据集或模型名称。
- 场景切换只需要 brief、实验代码和 adapter 配置。
- Docker 无网络执行、资源限制和产物挂载经过真实验证。

### 选择条件

如果首要问题是确认项目架构能否承担更多 AI 研究类型，应选择此方案。它会产生最直接的架构反馈，但不会显著增强单个研究任务的智能程度。

## 方案 E：本地模型与成本控制

### 目标

让 pipeline 能在本机 Qwen 模型上运行，并在远程 API 与本地模型之间按阶段配置；同时将 token、请求和实验资源统一计入预算。

### 工作内容

1. 用 vLLM 或同类服务托管本机 Qwen3 4B/8B/14B，提供 OpenAI 兼容接口。
2. 增加 provider 配置文件、健康检查、模型能力探针和失败回退。
3. 记录每阶段输入、输出、缓存 token、延迟和价格表版本。
4. 支持模型调用数、token、金额、墙钟时间、CPU/GPU 时间和磁盘用量上限。
5. 用固定研究产物比较本地模型与 `gpt-5.6-luna` 的结构化输出合格率、引用错误和审查质量。

### 交付物与验收

- 相同任务可在本地或远程模型下运行，无需修改研究工作流。
- 达到预算时可解释地停止，并能从阶段边界恢复。
- 有一份质量、速度和成本比较；不因本地模型响应格式差异破坏账本。

### 选择条件

如果 API 额度、隐私或离线使用是当前阻碍，应选择此方案。它主要改善部署与成本，对研究证据质量的直接提升较小。

## 建议顺序

推荐先选 **A：证据与引用系统**，之后进入 **B：长期研究记忆**。长期记忆依赖输入质量；先建立可定位、可验证的证据单元，后续记忆才能安全复用。

如果当前最关心的是减少 API 费用，则选择 **E**。如果希望尽快观察 agent 自主改进实验的能力，则选择 **C**。如果希望先验证架构是否通用，则选择 **D**。

确定方案后，为所选路线单独写 V2 实施计划、非目标和验收用例；本文件中的其他方案继续保留为候选，不并行开发。
