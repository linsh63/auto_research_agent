# v1.6 最终规划：公共科研能力与跨系统 SSH Worker

状态：**实施中。U、V、W 已完成；X–Z 待实施。** 目标版本为 `1.6.0`，按 **U → V → W → X → Y → Z** 执行，每阶段独立验收、记录、提交、推送并停止。

## 1. 版本目标

v1.6 将 v1.5 的 Linux 验收核心升级为：

> 在 macOS 和 Linux 上均可开发与运行 Core Service；当任务需要 Bubblewrap、CUDA 或 Linux 工具链时，macOS 客户端通过系统 OpenSSH 安全连接用户自己的 Linux 服务器，由远程 Worker 执行，Project 状态和科研门禁仍由同一个本地核心控制。

本版本同时完成 v1.5 T3 暴露的公共科研 API 缺口，并补齐最后两个 partial 维度。v1.6 不开发 Web、游戏或正式 CLI 产品，也不提供中心化云服务。 Windows 原生 Core/Worker 明确列为非目标，现有防御性识别不构成支持承诺。

## 2. 已确定的架构选择

### 2.1 复用系统 OpenSSH

- macOS、Linux 使用系统 `ssh`/`sftp`。Windows 不属于 v1.6 支持范围。
- 不引入自研 SSH 协议，不以 Node `ssh2` 作为默认传输，不要求 Docker。
- 复用用户的 `~/.ssh/config` Host alias、IdentityFile、ProxyJump、证书和系统 ssh-agent/keychain。
- 用 `ssh -G <alias>` 解析有效配置；进程调用只传参数数组，禁止拼接 shell 字符串。
- `ControlMaster` 只作为可选优化，不能成为正确性依赖。

OpenSSH 原生支持远程命令、端口转发、ProxyJump、BatchMode、连接超时和连接复用。参考：[OpenSSH ssh](https://man.openbsd.org/ssh)、[ssh_config](https://man.openbsd.org/ssh_config)。

### 2.2 本地 Core，远端 Worker

首版固定拓扑：

```text
macOS / Linux client
┌────────────────────────────────────┐
│ Core Service + SQLite + local CAS  │
│ SshWorkerBridge                    │
└──────────── SSH stdio/SFTP ────────┘
                    │ outbound only
                    ▼
┌────────────────────────────────────┐
│ User-owned Linux SSH host          │
│ versioned remote worker            │
│ Bubblewrap / CUDA / Linux tools    │
│ remote workspace + staging CAS     │
└────────────────────────────────────┘
```

- Core 不绑定公网地址，不通过 SSH 反向隧道暴露完整 REST 服务。
- SSH bridge 在本地持有 Core client；远端进程只收到当前 Worker 会话所需的版本化 JSONL frame。
- 现有 `worker.claim/heartbeat/log/complete/fail/recover` 语义保持唯一真源。
- lease token 可以经过加密 SSH 通道，但不进入命令行、环境、磁盘或日志。
- 远端只运行固定 launcher，不接受用户输入拼成的任意 shell command。

这借鉴 VS Code Remote SSH 的成熟分层：客户端通过 SSH 在目标机安装版本化远端组件，主要工作在远端执行，通信留在认证 SSH 通道。参考：[VS Code Remote SSH](https://code.visualstudio.com/docs/remote/ssh)。

### 2.3 控制与大文件分离

- 控制面、heartbeat、日志和取消：单条持久 SSH stdio channel，使用带长度或逐行 JSON frame 的协议。
- 文件面：SFTP，先上传 `.partial`，校验 SHA-256/大小，再原子 rename。
- 不把 SSHFS 作为运行依赖；不以 rsync 作为正确性基础。rsync 可作为后续可选加速器。
- 已存在服务器的数据使用管理员配置的 `remoteDataAlias`，Job 只引用 alias + manifest hash，不接收任意绝对路径。
- 小型输入和 Artifact 使用内容地址同步，只传远端缺失的 hash。

VS Code 文档也区分远端执行与 SSHFS/rsync 文件工作流，并指出批量文件更适合同步而非远程挂载；本项目进一步用 CAS hash 保证科研制品一致性。

## 3. 核心对象与公共契约

### 3.1 PlatformCapabilitySnapshot

服务与 Worker 分别报告：

- OS、arch、Node/Python 版本；
- executors：`python`、`bubblewrap`、`pi`；
- GPU vendor/device/count；
- sandbox、resource-limit、process-group 和 filesystem 能力；
- SSH client/version、SFTP、ProxyJump、multiplexing 是否可用；
- 本地/远端 workspace 与 Artifact transport；
- 每项状态：`available`、`unavailable`、`degraded`、`not_checked`，附原因。

调度必须匹配 capability；Mac 缺少 Bubblewrap 只能使相关 Job `unavailable`，不能使整个 Core 不可用。

### 3.2 SshHostProfile

只保存非 secret 配置：

- profile ID、显示名、SSH Host alias；
- remote root、预期平台/arch；
- 已批准 host-key fingerprint 与 known-hosts 状态；
- remote worker channel/version/hash；
- 允许的 executors、GPU 和数据 alias；
- 连接/keepalive/idle timeout；
- enabled/disabled/quarantined 状态。

不保存私钥、密码、key passphrase、ssh-agent socket 或完整 Core bearer token。Profile 默认 Workspace scope；Project 需显式纳入并锁定 profile ID、worker version 和 capability snapshot。

### 3.3 RemoteWorkerInstallation

安装到：

```text
~/.auto-research-agent/workers/<protocol-version>/<content-hash>/
```

本地先生成 release manifest；通过 SFTP 上传临时目录；远端校验 hash、Node/Python 和 Linux 前置条件后原子启用。升级并存安装，不覆盖正在运行的版本；失败回滚到旧 hash。离线服务器允许用户提供本地 worker bundle，不强制远端联网下载。

### 3.4 PortableWorkspaceSpec

Job 不再假设本地绝对路径在远端存在：

- `workspaceMode`: `local`、`cas_sync`、`remote_existing`；
- input artifacts：hash、大小、access、目标相对路径；
- remote data：alias、manifest hash、只读目标；
- output artifact declarations；
- executor、资源与时间墙；
- platform constraints。

路径解析必须阻止 `..`、symlink escape、盘符/UNC 混淆和大小写碰撞。

## 4. SSH 安全决定

1. 首次连接是人工 trust gate：显示 SHA-256 host fingerprint，用户确认后写项目独立 known-hosts；自动任务使用 `StrictHostKeyChecking=yes`。
2. 禁止 `StrictHostKeyChecking=no`，禁止自动静默替换变更的 host key；变化进入 quarantine。
3. 自动运行使用 `BatchMode=yes`、`ExitOnForwardFailure=yes`（若启用转发）、`ConnectTimeout`、`ServerAliveInterval` 和 `ServerAliveCountMax`。
4. 默认 `ForwardAgent=no`、`ForwardX11=no`、`PermitLocalCommand=no`；OpenSSH 官方文档明确提示 agent forwarding 会允许远端借用本地 agent 进行签名。
5. 私钥和 passphrase 交给系统 OpenSSH/ssh-agent/Keychain；核心只调用 Host alias。
6. 远端 launcher 使用固定命令和协议版本；所有变量走 frame，不进入 shell 解析。
7. worker 安装包和每个输入/输出均做本地与远端 SHA-256 双校验。
8. confirmation capability 仍一次性消费；远端只挂载批准的 `remoteDataAlias`，不得把 sealed 数据复制回客户端。
9. 每次连接、指纹批准、安装、Job、传输、取消、重连和清理进入审计；命令参数中的 token/secret 必须脱敏。
10. SSH 主机是用户信任边界。多租户或不可信服务器不在 v1.6 保证范围内。

## W：SSH host、安装与 stdio Worker

### 交付

- 系统 OpenSSH preflight：`ssh -V`、`ssh -G`、连接和目标平台探测。
- Host profile CRUD、fingerprint approval、known-hosts quarantine。
- versioned remote Worker bundle、SFTP staging、hash 校验和原子安装。
- `SshWorkerBridge`、JSONL/frame transport、heartbeat/log/cancel/recover。
- 固定 launcher 和无交互 BatchMode；支持用户 SSH config/ProxyJump。

### 门禁

- Linux 客户端连接真实 Linux sshd，安装并启动精确 hash 的 Worker；macOS arm64/x64 原生验证系统 OpenSSH config 与相同 stdio protocol。完整 macOS→Linux 科研 Job 留给 X/Z。
- 错误 host key、版本、hash、平台或 launcher 全部 fail closed。
- 断开 SSH 后 lease 按 resumable 规则恢复，旧 session 不能提交结果。
- 不开放 Core 监听地址，不传完整服务 bearer token。

**停止点：** W 报告、提交、推送后停止。

## 6. 明确不采用的方案

- **在 macOS 模拟 Bubblewrap。** 平台缺失必须显式，由 Linux Worker 提供真实边界。
- **把任意 SSH shell 当 Worker。** 这会绕过 lease、资源、失败和 Artifact 协议。
- **Core 直接保存私钥或密码。** 凭据由系统 OpenSSH 管理。
- **默认开放反向端口到本地 Core。** 首版使用 stdio bridge，减少 token 和监听面。
- **把 Docker 设为必需。** Linux Bubblewrap 和 SSH Worker 独立于 Docker 权限。
- **把 SSHFS/rsync 设为科学制品真源。** 正确性由 manifest、CAS 和 SHA-256 保证。
- **以 mock 平台替代真实发布验收。** mock 只用于单元测试。

## 7. 完成定义

v1.6 只有在 U、V、W、X、Y、Z 全部通过后完成。最终用户可以在 macOS 或 Linux 上运行同一个核心；本地可用能力直接执行，需要 Linux 的能力由显式批准的 SSH Worker 执行；任何缺失、降级、数据传输或权限扩大均可见、可审计、可撤销。
