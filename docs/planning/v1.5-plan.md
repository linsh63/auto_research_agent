# v1.5 规划：Headless Research Kernel 产品化

状态：实施中。N–S 阶段已完成；T 待实施。

| 阶段 | 状态 |
| --- | --- |
| N：公共契约与包边界 | 已完成 |
| O：Project 存档、事件与分支 | 已完成 |
| P：聊天、候选与执行策略 | 已完成 |
| Q：Job/Worker 与 Pi 复用 | 已完成 |
| R：Scenario SDK | 已完成 |
| S：Core Service 与客户端 SDK | 已完成 |
| T：迁移、能力基准与发布 | 待实施 |

## 1. 版本定位

v1.5 的唯一主目标是把现有可审计科研流水线升级为可独立部署、可持续演进、可被多个软件复用的 **Headless Research Kernel**。

本版本不开发正式 Web 工作台和科研游戏。只保留一个最小参考 CLI，用它验证聊天、候选行动、事件流、审批和长任务接口。正式 CLI、Web、游戏和项目导航属于 v2.0 项目集。

### v1.5 与 v2.0 的边界

| 版本 | 交付范围 |
| --- | --- |
| v1.5 | 升级后的独立核心、Core Service、公共协议、TypeScript/Python SDK、Job/Worker、Scenario SDK、Pi 插件目录与接入能力、项目存档与能力基准 |
| v2.0 | v1.5 核心正式版，以及基于核心完成的 CLI、Web 工作台、带插件商城界面的科研探索游戏和项目导航页 |

所有产品保持独立仓库、独立版本和独立部署。项目导航页只提供说明、兼容信息和跳转链接，不集中托管项目源码。

## 2. 当前基础与主要差距

### 已有基础

- 问题、证据、假设、协议、baseline、探索、候选冻结、确认、统计、评审和发布链路已经跑通。
- SQLite 状态、数据迁移、FactLedger、ScientificDecision、封存数据和 Bubblewrap 门禁已经可用。
- Pi SDK 已用于模型 Provider、会话、工具和结构化模型输出。
- v1.4 已完成三模板、三任务、三模型的真实研究，并验证失败诊断和受限发布。

### 阻碍多个软件复用的差距

1. 具体研究目录仍直接导入内部 Store、Workflow 和迁移文件。
2. 缺少稳定、版本化的公共命令、查询、事件和错误协议。
3. 自由聊天、候选节点和脚本调用尚未统一为同一种行动对象。
4. 长实验依附于当前进程，缺少持久化 Job、Worker、取消和恢复语义。
5. 缺少正式 Scenario 插件接口和 Python 开发入口。
6. 当前状态更接近 CRUD 快照，尚未形成面向多客户端的追加式事件流。
7. 项目不能以标准存档格式可靠导出、复制、分支和迁移。
8. 缺少可跨版本比较的 Research Capability Benchmark。
9. 根 CLI、真实研究脚本和核心内部接口耦合，不能作为公共 SDK 的兼容性证明。

## 3. 已确定的产品原则

### 3.1 核心独立

- 核心继续作为独立开源项目维护和发布。
- 核心不包含正式产品前端。
- 客户端不得直接访问数据库、内部 Store 或内部 Workflow。
- 科研能力升级由核心和插件完成，客户端只理解稳定的公共对象。

### 3.2 独立部署

- 每位用户部署自己的 Core Service。
- 首版不建设中心化云平台、账号系统或官方托管服务。
- CLI、Web 和游戏连接用户自己的本地或远程自托管实例。
- 默认完全本地、无遥测；外部模型、检索和网络访问必须显式启用并留下事件记录。

### 3.3 两种交互方式共存

- CLI 默认保持 Codex 式自由聊天。
- 用户可以开启候选模式，让核心返回多个合法研究节点。
- 候选模式始终提供“自由输入/其他行动”。
- 聊天输入、候选点击和 API 命令最终都转换为统一 `ResearchAction`。

### 3.4 科研门禁由核心强制

- 客户端可以影响预算、探索路线和候选选择。
- 客户端不能绕过范围、协议、候选冻结、确认隔离、统计、事实审计或发布门禁。
- `ExecutionPolicy` 可以控制门禁之间采用手动、候选选择或自动策略。

### 3.5 持续演进

- 核心状态机和公共协议保持稳定。
- 检索、记忆、选题、实验策略、评审器和领域场景通过版本化 Capability、Policy 与 Scenario 扩展。
- Agent 不得自动修改核心代码或强制门禁。

### 3.6 用户自由选择 Pi 插件

- 用户可以从本地目录、仓库链接或已配置的 Pi 插件来源发现插件。
- 核心提供统一的搜索、查看、安装、启用、禁用和版本锁定能力。
- 插件默认按 Project 纳入；用户也可以明确提升为 Workspace 可用插件。
- 搜索或查看插件不会执行插件代码。
- 纳入前必须展示功能、工具、skills、apps、MCP 依赖、权限、网络和文件副作用、许可证、来源、版本及兼容状态。
- 插件不能因为来自 Pi 生态而自动获得信任；实际权限仍由核心 Capability 和 ExecutionPolicy 决定。
- 游戏中的“插件商城”只是该核心目录的趣味化界面，不要求官方集中托管或商业化插件市场。

## 4. 目标分层

v1.5 将主项目收敛为以下六个可发布层次：

1. **Contracts**：公共 schema、命令、查询、事件和错误。
2. **Kernel**：科研领域对象、状态机、门禁和策略接口。
3. **Application**：用例编排、聊天行动解析、候选生成和投影更新。
4. **Runtime**：Pi、Capability、Job、Worker、沙箱、模型和检索适配。
5. **Service/SDK**：本地服务、TypeScript SDK、Python SDK、流式客户端。
6. **Scenario**：通过公共 Scenario SDK 接入的具体科研场景。

依赖方向固定为：`Scenario/Clients → SDK/API → Application → Kernel → Contracts`。Infrastructure 实现 Kernel/Application 定义的端口，不能反向污染公共协议。

## 5. 目标仓库结构

v1.5 允许在当前仓库内逐步迁移到 workspace，不进行一次性重写：

```text
packages/
├── contracts/          # JSON Schema、事件、命令、查询、错误
├── kernel/             # 领域对象、状态机、门禁、Policy 接口
├── application/        # 用例与行动编排
├── runtime/            # Pi、Worker、沙箱、检索、模型 Provider
├── server/             # 本地 REST + WebSocket Core Service
├── sdk-typescript/     # 官方 TypeScript SDK
└── scenario-sdk/       # 场景与 Capability 契约
python/
├── research_sdk/       # Python 客户端 SDK
└── worker/             # 官方本地 Python Worker
examples/
└── reference-cli/      # 只用于公共接口验收
```

迁移期间原 `src/` 继续工作。新包先包装现有能力，通过兼容测试后再移动实现，避免破坏已经完成的科研门禁。

## 6. 公共领域协议

### 6.1 核心对象

- `Workspace`：本地用户空间和隔离边界。
- `Project`：一个研究存档。
- `Actor`：触发命令的人、Agent、Worker 或系统策略。
- `ResearchAction`：一次结构化研究行动。
- `ResearchNode`：当前可探索或已经完成的研究节点。
- `ResearchEvent`：不可覆盖的事实事件。
- `Job`：可排队、取消、恢复的长任务。
- `Approval`：人与策略产生的门禁决定。
- `Artifact`：带内容哈希、来源和访问级别的制品。
- `Capability`：带权限、预算和失败语义的能力。
- `Scenario`：领域研究插件及其输入输出契约。
- `ExecutionPolicy`：手动、候选选择和自动执行的组合策略。
- `PluginSource`：本地、仓库或 Pi 插件来源。
- `PluginDescriptor`：插件功能、版本、依赖、权限、许可证和兼容元数据。
- `PluginInstallation`：插件在 Workspace 或 Project 中的安装、启用和锁定状态。

### 6.2 Command / Query / Event

- Command 负责请求状态变化，必须携带 Workspace、Project、Actor、幂等键和 schema 版本。
- Query 只读，返回面向客户端的稳定 read model，不能暴露数据库结构。
- Event 追加写入，至少包含事件版本、因果命令、关联 ID、Actor、时间和 payload 哈希。
- 所有命令返回接受、拒绝或排队结果；科研门禁拒绝必须使用稳定错误码。
- 历史事件通过 upcaster 升级，禁止直接改写已落盘事件。

## 7. 项目存档与研究分支

### 7.1 存档语义

一个 Project 对应一个独立研究存档，包含：

- 研究事件流；
- 当前 read model；
- 协议、假设、决策和审批；
- Job 与 Worker 状态；
- 报告、日志和 Artifact 索引；
- 插件、模型和环境版本；
- 项目级记忆。

### 7.2 分支

- 任意合法研究节点可以 fork 新分支。
- 分支拥有独立预算、状态、事件和候选。
- 原分支历史不可覆盖或删除。
- 同一个确认数据角色只能由符合协议的冻结分支使用。
- 最终发布必须明确来自哪个分支和候选冻结。

### 7.3 Research Project Bundle

标准 Bundle 至少包含 manifest、事件、公共对象、报告、哈希和依赖清单。大型数据、模型和私有制品支持：

- 内嵌；
- 外部内容地址；
- 缺失但可验证；
- 因权限不可导出。

导入必须先做 schema、哈希、权限和核心版本兼容检查，不能静默修复科研状态。

## 8. 统一聊天与候选行动

### 8.1 自由聊天

聊天由 `ConversationSession` 保存，但聊天文本本身不直接改变科研状态。模型必须输出：

- 普通回答；或
- 一个待执行 `ResearchAction`；或
- 多个 `ResearchActionCandidate`。

产生状态变化的行动必须经过 Kernel 验证并写入事件。

### 8.2 候选模式

候选项至少提供：

- 标题和说明；
- 依据的事实与假设；
- 预期信息增益；
- 成本和预计时间；
- 风险与停止条件；
- 所需权限；
- 是否触发人工门禁。

候选列表始终追加自由输入选项。自由输入重新进入行动解析，不要求用户只能选择已有节点。

## 9. ExecutionPolicy

提供三种可组合模式：

- `manual`：行动执行前由用户确认。
- `candidate`：核心生成候选，用户选择或自由输入。
- `auto`：策略在预算和权限内自动选择行动。

以下门禁默认不可关闭：

1. 研究范围批准；
2. 确认性协议批准；
3. 候选冻结与确认能力签发；
4. 最终主张和发布批准。

未来可以通过显式高级策略调整，但客户端不能自行跳过。

## 10. Job 与 Worker

### 10.1 先调研 Pi

实现前必须对 Pi 及其插件做一次有记录的复用审计，重点检查：

- 长任务和后台进程；
- 会话恢复；
- 事件与流式输出；
- 取消和超时；
- 工具生命周期；
- 插件权限；
- 可复用的任务状态结构。

能够直接复用的部分不得重新实现。差异通过 ADR 记录。

### 10.2 科研 Job 补充

Pi 未覆盖的部分由核心提供：

- 持久化队列；
- 幂等提交；
- Worker 租约和心跳；
- GPU、CPU、内存、磁盘和时间墙；
- stdout/stderr 与结构化进度流；
- cancel、retry、resume；
- 环境失败、数据失败、科学失败和预算失败分类；
- Artifact 原子提交；
- exploration 与 confirmation 不同权限。

首版只实现本地 Worker，但协议不能假设 Worker 与 Core Service 同进程或同机器。

## 11. Scenario SDK

### 11.1 正式接口

每个 `ResearchScenario` 通过公共 SDK 提供：

- `DataAdapter`：数据清单、角色、封存和单位定义；
- `ExperimentRunner`：Job 描述与运行要求；
- `Evaluator`：确定性解析、评分和缺失语义；
- `Analyzer`：estimand、聚类单位、统计和敏感性分析；
- `DomainCapability`：可选领域工具；
- `ScenarioManifest`：版本、兼容范围、权限、预算和制品声明。

插件不能：

- 直接打开核心数据库；
- 修改历史事件；
- 绕过确认令牌；
- 直接发布主张；
- 读取未授权密钥或其他 Workspace。

### 11.2 双语言支持

- TypeScript SDK 用于核心扩展、服务和客户端集成。
- Python SDK 用于数据、模型、统计和实验场景。
- 两个 SDK 从同一份 JSON Schema/OpenAPI 生成公共类型。
- 科研规则只在 Kernel 实现，Python SDK 不复制状态机。

### 11.3 Pi Plugin Bridge 与插件目录

核心提供 `PiPluginBridge`，把 Pi 插件贡献的 skills、tools、apps 和 MCP 能力转换为核心 `Capability`，但不复制 Pi 已有的插件实现。

插件目录支持：

- `searchPlugins(query, filters)`：按名称、领域、功能、权限、来源和兼容版本搜索；
- `inspectPlugin(id, version)`：查看说明、能力、依赖、权限、许可证、维护者和来源；
- `installPlugin(...)`：解析并固定版本与内容哈希；
- `enablePlugin(...)`：在 Project 或 Workspace 范围启用；
- `disablePlugin(...)`：停止后续调用但保留历史事件；
- `updatePlugin(...)`：显式升级并生成兼容和权限差异；
- `removePlugin(...)`：移除安装但不删除历史研究中的版本记录。

生命周期至少包括：`discovered → inspected → installed → enabled/disabled`，以及 `incompatible`、`failed`、`quarantined` 状态。

安装与启用规则：

1. 搜索和 metadata inspection 必须保持只读。
2. 安装前展示新增权限、依赖和副作用。
3. 默认拒绝静默自动更新；Project Bundle 锁定实际插件版本和哈希。
4. 插件升级后权限扩大时必须重新获得用户批准。
5. 未验证插件默认在受限环境运行；实验执行继续使用 Worker 和沙箱。
6. 插件不能读取 confirmation 数据，除非当前冻结协议和能力令牌明确授权。
7. 插件不能直接写 ResearchEvent；只能提交命令，由 Kernel 验证后产生事件。
8. 插件来源不可用时，历史 Project 仍能读取，执行则明确进入 capability unavailable 状态。

目录可以聚合多个来源，但核心不对第三方插件质量作隐含背书。v1.5 只实现目录、接入和权限后端；正式商城交互归入 v2.0 游戏和 Web 产品。

## 12. Core Service 与 SDK

### 12.1 Core Service

- 默认监听 localhost。
- REST 用于命令与查询。
- WebSocket 或等价流用于事件、聊天 token、Job 日志和候选更新。
- 本地客户端可以自动启动服务并发现端口。
- 远程地址作为配置存在，但 v1.5 不实现云账号平台。

### 12.2 安全边界

- 默认无遥测。
- 网络、文件、模型调用、实验执行、确认数据和发布均为独立权限。
- 密钥只通过运行时 secret provider 注入，不进入事件、Bundle、日志或报告。
- 社区 Capability 默认只读；实验代码默认进入沙箱。
- 每个事件记录实际使用的权限和外部服务，不记录 secret 值。

## 13. 记忆与持续学习

- 项目内记忆默认开启，并属于 Project 存档。
- 跨项目记忆默认关闭。
- 只有经过事实审计、作用域声明和用户批准的经验才能提升到 Workspace 记忆。
- 候选配置、未验证推断和确认后调参不能进入全局策略。
- 记忆必须记录来源 Project、适用条件、失效条件、证据和版本。
- Agent 可以建议核心或插件改进，不能自动修改核心代码或强制门禁。

## 14. 公共兼容与发布

- 公共协议采用语义化版本。
- Command、Query、Event 和 Bundle 均带 schema 版本。
- SDK 必须具有跨版本契约测试。
- 数据库迁移先备份，失败原子回滚。
- 旧事件使用确定性 upcaster；没有 upcaster 时 fail closed。
- 服务提供 capability negotiation，客户端在启动时检查核心和插件兼容性。
- v1.5 发布前不承诺内部模块路径稳定，但公共包不得依赖内部路径。

## 15. Research Capability Benchmark

建立非单一总分的能力矩阵，至少覆盖：

1. 研究问题与范围；
2. 文献检索和全文证据；
3. 创新性与最近工作边界；
4. 竞争假设和可证伪预测；
5. 实验设计与混杂识别；
6. baseline 和实验执行；
7. 序贯决策与停止判断；
8. 统计和实验单位；
9. 失败诊断；
10. 记忆提升与作用域；
11. 科学写作与事实一致性；
12. 复现与发布门禁。

每项保存输入、期望性质、机器门禁、人工评价和制品哈希。发布报告同时提供能力基准、真实研究和工程门禁，不能用单个成功课题代表完整科研能力。

## 16. 实施阶段

### N：公共契约与包边界

- 建立 Contracts、Kernel、Application 的公共边界。
- 定义核心对象、错误码和版本策略。
- 为现有 Store/Workflow 加兼容 facade。
- 建立“公共包不得导入内部模块”的依赖测试。

**门禁：** 最小研究可以只通过公共 Application API 创建、查询和推进；旧测试保持通过。

### O：Project 存档、事件与分支

- 实现 Workspace、Project、Actor 和追加事件日志。
- 建立 read model 投影、幂等命令和事件 upcaster。
- 实现 fork 和 Bundle 导入导出。

**门禁：** 项目可复制、恢复和分支；原历史不被覆盖；损坏 Bundle 被拒绝。

### P：聊天、候选与执行策略

- 将聊天、候选点击和 API 调用统一为 ResearchAction。
- 实现 ConversationSession 和候选 read model。
- 实现 manual、candidate、auto 策略。
- 自由输入始终可用。

**门禁：** 三种入口产生相同事件和门禁结果；客户端无法绕过强制审批。

### Q：Job/Worker 与 Pi 复用

- 完成 Pi 实现和插件审计。
- 实现持久化 Job、日志流、取消、恢复和资源租约。
- 实现本地 Python Worker。
- 将 Bubblewrap 执行纳入 Worker 协议。

**门禁：** 服务重启后 Job 可恢复；取消和超时释放资源；confirmation 权限保持封闭。

### R：Scenario SDK

- 发布 TypeScript Scenario SDK 和 Python Worker/Scenario SDK。
- 将数据、实验、评分、分析和 Capability 契约化。
- 实现权限检查与兼容协商。
- 实现 PiPluginBridge、插件来源、可搜索目录、安装/启用/禁用和版本锁定。

**门禁：** 场景插件不导入任何内部 Store、Workflow 或 migration 文件；搜索插件不执行代码；权限扩大和不兼容插件被门禁阻止。

### S：Core Service 与客户端 SDK

- 实现 REST、事件流和本地服务生命周期。
- 发布 TypeScript SDK 和 Python SDK。
- 实现最小参考 CLI。
- 加入离线默认、secret provider 和权限审计。
- 为参考 CLI 提供插件搜索、详情、安装、Project 纳入、禁用和自由输入命令。

**门禁：** 参考 CLI 只通过 SDK 完成聊天、候选、Job、审批和报告流程。

### T：迁移、能力基准与发布

- 迁移多模态案例和一个不同类型案例。
- 建立 Research Capability Benchmark 基线。
- 完成 Bundle 跨实例迁移。
- 验证 Bundle 可以锁定插件版本与哈希，并在另一实例报告缺失或不兼容插件。
- 编写 Apache-2.0、CONTRIBUTING、扩展教程、模板和 ADR/RFC 流程。
- 运行完整兼容、迁移、故障注入和真实研究验收。

**门禁：** 两个真实案例只使用公共 SDK；核心具备独立部署、独立升级和社区扩展能力。

## 17. 全局验收标准

v1.5 只有同时满足以下条件才能完成：

1. 核心可以作为无界面服务独立启动、停止和恢复。
2. 公共 TypeScript/Python SDK 均能创建、读取和推进 Project。
3. 自由聊天、候选模式和直接命令共享 ResearchAction。
4. 候选模式始终保留自由输入。
5. Project 支持事件重放、fork、导出、导入和哈希检查。
6. Job 支持持久化、日志、取消、恢复、超时和资源租约。
7. 至少两个真实 Scenario 不导入核心内部模块。
8. CLI 参考实现不接触数据库和内部 Workflow。
9. exploration/confirmation 隔离、FactLedger、四维评审和发布门禁不回退。
10. 默认无遥测；网络和外部模型调用可审计、可禁用。
11. 旧数据库迁移和旧 CLI 兼容路径有自动测试。
12. Research Capability Benchmark 形成首个可重复基线。
13. 用户可以搜索、查看并自由选择 Pi 插件，插件默认以 Project 范围启用。
14. 插件功能、权限、依赖、来源、许可证、版本和兼容状态在纳入前可见。
15. 插件版本和哈希进入 Project Bundle；权限扩大需要重新批准。
16. 全量类型检查、测试、文档、迁移、故障注入和发布审计通过。

## 18. 非目标

v1.5 不包括：

- 正式 CLI 产品体验；
- Web 工作台；
- 科研探索游戏；
- 中心化账号、团队或云平台；
- 官方集中托管、付费交易、推荐排序或商业化插件市场；
- 广义湿实验和真实设备自动化；
- 自动修改核心代码和科研门禁；
- 仅为了展示而弱化确认、统计或审计要求。

## 19. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 重构导致已有科研能力回退 | facade 迁移、契约测试、双案例重放 |
| 事件系统复杂度过高 | 先支持单机 SQLite 事件日志和确定性投影 |
| Pi 能力被重复实现 | Q 阶段先完成复用审计和 ADR |
| TypeScript/Python 规则漂移 | 单一 schema，科研规则只在 Kernel |
| 插件绕过门禁 | 权限 manifest、SDK 边界、沙箱与依赖测试 |
| 恶意或被接管的插件来源 | 内容哈希、版本锁定、权限差异、隔离执行、来源与许可证展示 |
| 商城界面诱导用户过度授权 | 默认 Project 范围、最小权限、启用前确认、随时禁用 |
| 自动策略误执行 | ExecutionPolicy、预算墙、强制人工门禁 |
| Bundle 泄露密钥或私有数据 | secret 排除、访问级别、导出审计、fail closed |
| 过早开发客户端绑死核心 | v1.5 禁止正式客户端，仅保留参考 CLI |

## 20. v2.0 项目集展望

v1.5 通过后再启动 v2.0：

1. 正式 Codex 式 Research CLI；
2. Web 科研工作台；
3. 以 Project 为存档、ResearchNode 为地图节点的科研探索游戏；
4. 独立项目导航页，收录官方与社区项目链接。

游戏本质仍是科研：用户可以选择节点、预算和分支，但科研事实、数据隔离、统计和发布门禁全部由核心控制。游戏提供类似商城的插件界面，用户可以搜索插件、查看功能与权限，并决定是否将其纳入当前 Project；商城调用的是 v1.5 的统一插件目录和安装 API。所有产品通过公共 SDK/API 使用同一个核心，并可随着核心科研能力升级而获得新能力。

## 21. v1.5 完成后的科研能力重点

核心产品化完成后，下一轮科研能力优先优化：

- 选题价值判断；
- 创新性和最近工作审计；
- 竞争假设；
- 混杂识别；
- 判别实验；
- 交叉格式和跨数据集验证；
- 经过审计的跨项目经验提升。

扩展更多学科和增强论文展示排在这些能力之后。
