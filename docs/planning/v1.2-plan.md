# Auto Research Agent v1.2 完整实施规划

状态：**已确认，待实施**

制定日期：2026-09-20

确认日期：2026-09-20

主题：从“可执行的科研流水线”升级为“能管理不确定性和多轮证伪的研究系统”

## 0. 已确认的产品决策

本节是实施约束。执行过程中不得自行放宽；确需改变时先写 ADR，说明证据、影响和迁移方案，再由研究者确认。

| 主题 | 已确认决策 |
| --- | --- |
| 完成定义 | v1.2 必须由一个真实 AI 研究任务端到端验收，不能只完成 schema 或 fixture |
| 正式范围 | 仅支持可脚本化的 AI/ML 计算实验；其他研究设计登记为未验证 profile |
| 任务入口 | 用户只给宽泛方向和硬约束；agent 提出3个候选问题，用户选择后形成正式问题 |
| 验收方向 | CIFAR-10/CIFAR-10-C 上的小型图像分类鲁棒性与校准 |
| 资源硬墙 | 单 GPU、12 GPU-hours、24小时墙钟、20GB新增磁盘、20次模型调用、10 USD |
| 确认证据 | 必须有 internal confirmation 和预声明 corruption robustness；v1.2 不强制第二数据集 |
| 主要指标 | agent 从批准目录选择唯一 primary outcome；其他指标预先标记 secondary/exploratory |
| 人工门 | scope、protocol、candidate freeze、final claim 四个门全部保留 |
| 统计范围 | paired repeated-run 与 `training seed × corruption group` 分层配对分析 |
| Reviewer | 可使用同一模型，但必须隔离 session、只读权限、输入快照和 rubric，并报告独立性等级 |
| 历史数据 | v1.1 run 只读兼容；只迁移可确定字段，不补造旧 protocol 或 confirmation 状态 |
| 实验执行 | 固定且经哈希审核的脚本可用受限 process；agent生成或修改的代码必须使用 bubblewrap 沙箱 |
| Docker | 不是发布条件；科研与执行边界验收优先于特定容器技术 |
| 结果要求 | 正结果不是发布条件；可信负结果、inconclusive 或有理由停止均可通过 |
| Confirmation 后迭代 | 当前 run 禁止继续调参；任何修改必须派生新 run，并记录已观察的结果 |
| 模型真实性 | 自动测试可用确定性 adapter；最终真实案例必须通过 pi 使用实际 LLM |
| 兼容模式 | 保留 v1.1 线性流程为 `smoke`；正式科研默认使用 `confirmatory` |

## 1. 核心判断

v1.1 已经证明系统能够保存证据、执行受控实验、记录结果、经过审查并生成可追溯报告。它目前更接近一个**可审计的单次实验工作流**：研究问题、baseline、candidate、指标和成功条件大多由 brief 预先给定，agent 负责依次填充阶段产物。

真实科研的主要难点还没有进入核心状态机：

1. 研究问题通常需要从宽泛方向逐步收敛，并判断是否值得研究、是否可回答。
2. 文献工作需要形成“已知事实—争议—空白—方法限制”的证据地图，而不是只得到一组相关来源。
3. 同一现象通常存在多个竞争假设，研究设计的目标是区分它们，不只是让一个候选超过基线。
4. 探索性试验和确认性试验必须分开；看到结果后形成的解释不能伪装成预先预测。
5. 一个均值或单一指标不能表达不确定性、效应大小、失败模式、计算代价和外部有效性。
6. 研究会反复回到检索、假设、设计和调试阶段，并可能以“证据不足”“问题不值得继续”或“需要外部数据”结束。
7. 最终产物应说明每项主张能达到什么证据等级，而不只是生成一份叙述流畅的报告。

因此，v1.2 的主目标不是扩大自动化范围，而是建立**研究协议、认知状态和探索/确认边界**。系统应能解释当前知道什么、不知道什么、什么结果会改变判断、下一项实验为什么最有信息价值，以及何时应该停止。

## 2. 已有基础与关键缺口

### 2.1 可以保留的基础

- SQLite 事实库、append-only 事件、内容寻址产物和运行恢复。
- Source → Passage → Claim 的证据链和最终 Claim 门禁。
- pi 模型适配、结构化输出、模型调用记录和 provider 配置。
- 人工计划审批、审查响应与最终确认。
- 受控实验命令、超时、源码快照、日志和数据/模型哈希。
- memory 生命周期、namespace 和 opt-in 策略。
- bounded search、节点 lineage、预算墙与 sealed final-test 概念。
- 文本与 CV 两个 adapter-only 场景。

### 2.2 当前实现与真实科研的差距

| 环节 | 当前实现 | 真实科研需要 | 严重度 |
| --- | --- | --- | --- |
| 任务入口 | brief 已包含具体问题和两个命令 | 从方向、约束和价值判断形成可回答的问题 | 关键 |
| 文献证据 | 搜索结果列表和 passage 检索 | 系统性查询、纳排标准、证据地图、矛盾和覆盖缺口 | 关键 |
| 新颖性 | 提示模型不要从摘要宣称 novelty | 明确贡献声明，逐项与最相近工作对照 | 关键 |
| 假设 | 单个 hypothesis | 多个竞争假设、null、机制解释和判别性预测 | 关键 |
| 实验设计 | baseline/candidate 与种子列表 | 实验单位、变量、混杂、抽样、功效、指标有效性和分析计划 | 关键 |
| 预注册 | 成功条件保存在 brief | 结果不可见前冻结 protocol，并记录任何偏离 | 关键 |
| 实验过程 | 一次 baseline 后一次 candidate | baseline 复现、pilot、探索、冻结、确认、复现和鲁棒性检查 | 关键 |
| 自动搜索 | C 阶段组件与主 ResearchEngine 分离 | 搜索节点由研究协议约束，并能回写假设和决策 | 重要 |
| 结果数据 | 主指标是单一 `number` | 原始观察、分布、置信区间、效应量、多指标与资源代价 | 关键 |
| 统计分析 | LLM 阅读 JSON 后给结论 | 预声明分析由代码执行，检查假设、缺失值和多重比较 | 关键 |
| 解释 | yes/no/inconclusive | 区分观测、统计推断、机制解释、因果主张和外推范围 | 关键 |
| 审查 | 一次模型审查 | 方法、统计、证据、复现和安全分维度审查；关键问题可退回前序阶段 | 重要 |
| 迭代 | `maxIterations` 固定为 1 | 有理由的分支、回退、停止和新 run 派生 | 关键 |
| Skills | 将若干 SKILL.md 截断片段拼入 prompt | 版本化能力、结构化输入输出、适用条件和执行证据 | 重要 |
| 记忆 | 终审后自动生成两条 verified memory | 只提炼可复用且有适用边界的程序、失败和证据 | 重要 |
| 协作 | 固定的两个审批点 | 对问题、protocol、确认实验、结论分别做有信息的审批 | 重要 |
| 可复现性 | 代码和日志有 hash | 环境、数据 lineage、统计脚本、随机性和一键重放清单 | 重要 |

### 2.3 目前最影响结论可信度的具体技术问题

- `ResearchEngine` 是线性 `switch`，不能表达退回、分支、并行证据工作和派生研究问题。
- `ExperimentSchema` 把研究压缩为一个 baseline 和一个 candidate；C 阶段搜索图没有接入主工作流。
- `maxIterations` 的 schema 是字面量 `1`，系统实际上无法进行研究迭代。
- `ExperimentResult.metric` 只有一个标量；`details` 是无约束 JSON，无法可靠执行统计门禁。
- `AnalysisSchema` 只有 `yes/no/inconclusive`，没有估计量、不确定性、假设检查或证据等级。
- hypothesis 的来源关系目前主要记录为 `background`，尚未表达哪些前提被什么 passage 支持或反驳。
- review 可以由同一 provider/model 完成，且独立性只体现在 prompt 角色，没有模型、上下文和权限层面的隔离证明。
- skill 只是方法文本注入；脚本能力、触发条件、产物和失败语义没有统一进入工作流。
- 当前真实案例的实验是有效的，但研究问题、命令和判断框架主要由开发者预写；它们验证了 pipeline，没有验证 agent 自主完成问题收敛和实验设计。

## 3. v1.2 目标与非目标

### 3.1 目标

v1.2 完成后，系统应能在一个给定研究方向内：

1. 形成并审批一个具体、可回答且有价值的研究问题。
2. 建立带纳排边界、矛盾和覆盖说明的 evidence map。
3. 同时维护至少一个目标假设、一个 null/保守解释和一个竞争机制解释。
4. 在看到确认数据前冻结 protocol、主要指标、分析方法和停止条件。
5. 先复现 baseline，再进行有界探索；冻结候选后使用未观察的 confirmation 数据验证。
6. 用确定性统计程序生成效应量、不确定性、诊断和多重比较记录。
7. 依据证据更新 hypothesis 状态，允许退回、派生新问题或以负结果停止。
8. 输出 claim–evidence–analysis 矩阵、研究日志和可重放包。

### 3.2 非目标

- 自动生成可直接投稿的论文。
- 追求任意 benchmark 的 SOTA。
- 用多 agent 对话数量替代实验和证据质量。
- 自动执行人体、动物、临床或其他需要伦理审批的实验。
- 无边界地修改任意代码、下载任意数据或增加算力。
- 在 v1.2 默认开启跨项目记忆。
- 同时解决所有学科的统计和实验设计问题。

## 4. 目标研究流程

v1.2 将工作流从固定流水线改成**有受控回路的研究状态图**：

```text
方向与约束
  ↓
问题收敛 ↔ 初步证据地图
  ↓ scope approval
竞争假设与判别性预测
  ↓
研究协议与分析计划
  ↓ protocol approval / protocol freeze
baseline 复现 → pilot / bounded exploration
  ↘ 失败诊断 ↗        ↓ candidate freeze
                     confirmation
                         ↓
                 统计分析与主张评估
                         ↓
              鲁棒性 / 复现 / 对抗审查
                 ↙          ↓          ↘
             修订问题     有界结论      停止
                 ↓
              派生新 run
```

同一个 protocol freeze 后不得回到探索阶段继续调参。看到 confirmation/test 后若需要修改假设或方法，必须派生新 run，并标记原结果已经被观察。

## 5. 各步骤的迭代设计

### 5.1 方向输入与问题收敛

**输入**：宽泛研究方向、目标用户或科学价值、允许的数据和算力、时间、隐私与禁止事项。

**新增能力**：

- 将 `ResearchBrief` 拆成 `ResearchIntent` 与经审批的 `ResearchQuestion`。
- 对问题检查具体性、可测量性、可证伪性、资源可行性和伦理/许可条件。
- 明确 target population、研究对象、干预或方法、对照、主要 outcome 和适用范围。
- 生成 `AssumptionRegister`，记录问题成立依赖的前提和失效条件。
- 可以输出 `not_researchable_now`、`already_answered` 或 `insufficient_access`，不强制进入实验。

**门禁**：scope approval。研究者确认问题、价值、边界和最高预算。

**验收**：给出三个宽泛方向时，系统能够分别形成可回答问题或给出有证据的停止理由；不得自行补造数据权限和资源。

### 5.2 文献检索与证据综合

**当前问题**：已有检索能找到 passage，但没有形成可判断研究空白的综合结构。

**新增对象**：`SearchProtocol`、`ScreeningDecision`、`EvidenceMap`、`EvidenceGap`、`ClosestWorkComparison`。

**流程**：

1. 先写查询族、来源库、年份、纳排标准和停止条件。
2. 去重后进行标题/摘要筛选，再对关键论文读取全文。
3. 按“问题、方法、数据、指标、结果、限制”抽取结构化条目。
4. 对相互支持和冲突的结论分别聚类，不以引用数量代替证据质量。
5. 对最相近工作做逐项差异矩阵；novelty 只能登记为 `unresolved`、`likely_overlap` 或 `supported_with_scope`。
6. 保存未获取全文、检索失败和可能遗漏的来源，报告 coverage gap。

**门禁**：关键研究前提只有摘要证据或检索覆盖不足时，不得进入确认性实验；允许进入标记为 exploratory 的 pilot。

**验收**：人工构造的支持、反驳、重复工作和不可访问全文都能进入正确位置；最终主张不得把背景引用当直接支持。

### 5.3 竞争假设与判别性预测

**新增对象**：`HypothesisSet`，包含 target、null、rival、assumptions、predictions、discriminatingObservations 和 updateRules。

**规则**：

- 每个主要假设至少有一个可信 rival 或明确说明为何不存在。
- prediction 必须对应可观察变量、方向、容许区间和时间点。
- 为每种可能结果预先写明如何更新各假设，避免结果出现后移动门柱。
- 假设状态使用 `proposed → testable → active → weakened/supported/refuted/unresolved`，状态变化必须引用 observation 或 evidence。
- 想法的新颖性、理论合理性和实验可检验性分别评分，不合并成模糊总分。

**验收**：同一结果可能同时削弱多个假设或无法区分假设；系统不能强迫选择“支持目标假设”。

### 5.4 研究设计与 protocol freeze

**新增对象**：`ResearchProtocol`、`StudyDesign`、`AnalysisPlan`、`DeviationPolicy`。

protocol 至少包含：

- 实验单位、采样总体、纳入/排除规则和数据 lineage；
- 自变量、因变量、控制变量、潜在混杂和控制方法；
- baseline 的来源、复现容差和失败处理；
- primary/secondary/exploratory outcomes；
- 最小有意义效应、样本量或重复数依据；
- 随机化、配对、分层、blinding 可行性和种子策略；
- 缺失值、异常值、失败 run 和 protocol deviation 的处理；
- 统计模型、假设诊断、多重比较控制和置信区间；
- pilot、exploration、confirmation、test/audit 的数据角色；
- 预算、停止条件和允许的搜索空间。

protocol approval 后生成内容哈希和冻结事件。任何实质修改创建新版本，记录原因、修改时间和当时已观察的数据。

**验收**：把确认集路径传给 exploration runner、观察结果后静默更换 primary metric、删除失败 seed 或扩大搜索空间都必须被门禁阻止。

### 5.5 Baseline 复现与校准

baseline 不再只是第一个可执行命令，而是一个单独阶段：

- 从论文或官方实现提取目标范围和允许差异。
- 验证数据、代码、依赖、硬件和指标实现。
- 与公开结果比较，超出 tolerance 时先进入 `reproduction_diagnosis`。
- 区分 environment failure、implementation mismatch、data mismatch、metric mismatch 和 published result not reproduced。
- baseline 未复现时，candidate 结果只能作为相对工程观察，不能宣称改进已发表方法。

**验收**：故意使用错误数据版本、错误指标方向和性能明显偏离的 baseline，系统必须停止或降级结论。

### 5.6 Pilot 与有界探索

pilot 用于发现管线错误、估计方差和校准资源，不用于确认主张。bounded search 进入主工作流，并增加：

- 每个 search node 关联 hypothesis/prediction/protocol version。
- planner 必须说明候选预期改变什么机制或失败模式。
- debug node 与 scientific candidate 分开计费和报告。
- validation 可用于选择；confirmation/test 永远不可用于候选排序。
- 所有尝试进入结果集，禁止只保留最佳节点。
- 搜索结束产生 `CandidateFreeze`，固定代码、配置、环境和分析计划。

**验收**：最佳结果、失败结果和调试结果计数能完全对账；同预算下与非自适应策略比较选择偏差和收益。

### 5.7 Confirmation、复现与鲁棒性

确认阶段只运行冻结候选，并使用未被 exploration 观察的数据或预声明的新随机重复。

分为三类证据：

- **internal confirmation**：相同任务、未观察数据；
- **robustness**：预声明扰动、子群、指标或实现变化；
- **external replication**：不同数据、代码路径或执行环境。

每类失败都保留，并决定 claim 的外推范围。v1.2 至少要求 internal confirmation；高强度“通用改进”主张还必须有 robustness 或第二场景复现。

### 5.8 统计分析

LLM 负责解释分析计划和诊断建议，数值结果必须由版本化代码生成。

**新增结构**：

- `ObservationTable`：每个实验单位的原始指标和缺失原因；
- `StatisticalEstimate`：估计量、effect size、standard error/interval、方法和假设；
- `DiagnosticResult`：独立性、分布、方差、收敛和异常检查；
- `MultiplicityRecord`：全部比较、family 和校正方法；
- `SensitivityAnalysis`：合理分析选择变化后的结果。

**规则**：

- primary outcome 必须报告原始差值、效应量和区间；p-value 可选且不能单独决定结论。
- 不独立的 seed、fold、样本和数据集要按正确实验单位分析。
- non-significant 不自动等于无效；需要区间或等效性边界支持。
- 违反分析假设时使用预声明 fallback，不能临时试多个检验后挑选结果。
- exploratory analysis 必须带标签，并生成新的待验证 hypothesis，不能升级为 confirmed claim。

**验收**：使用包含缺失 run、异常值、相关重复和多指标的 fixture，统计结果与独立参考实现一致。

### 5.9 解释、主张分级与决策

每条最终主张建立 `ClaimAssessment`：

```text
claim
├── scope / population / conditions
├── evidence supporting and opposing
├── protocol and analysis versions
├── effect estimate and uncertainty
├── alternative explanations
├── validity threats: internal / construct / external / statistical
└── grade: observed | suggestive | supported | replicated | unresolved | refuted
```

禁止从“validation 更好”直接跳到“方法普遍有效”。系统分别判断：

- 数据中观察到了什么；
- 统计上能估计什么；
- 是否支持机制解释；
- 能推广到哪些数据、任务和环境；
- 哪些证据会推翻当前判断。

决策输出不是只有 continue/stop，而是：`collect_evidence`、`redesign`、`debug_reproduction`、`explore`、`confirm`、`replicate`、`publish_bounded_result`、`stop_low_value`、`stop_inconclusive`。

### 5.10 对抗审查、研究者交互与报告

审查拆为四个独立维度：

1. evidence review：引用是否支持主张、是否遗漏反证；
2. methods review：设计能否回答问题、是否存在混杂和泄漏；
3. statistics review：实验单位、假设、效应量、区间和多重比较；
4. reproducibility review：代码、数据、环境和运行清单是否完整。

reviewer 使用只读工具，不得修改实验或分析产物。关键问题能将 run 退回指定阶段；修复后保留旧版本和响应。

报告分为：研究问题、证据地图、冻结 protocol、偏离记录、全部实验、统计结果、claim matrix、反证与限制、停止/继续理由、复现清单。科学写作只消费已通过门禁的对象，不能在写作阶段新增事实。

## 6. 建议的数据与架构改造

### 6.1 从线性状态机改为版本化研究图

保留顶层 phase，内部任务使用有向图：

```text
ResearchProgram
 ├─ ResearchQuestion v1..n
 ├─ EvidenceMap v1..n
 ├─ HypothesisSet v1..n
 ├─ ResearchProtocol v1..n [draft/frozen/deviated/closed]
 ├─ Study / SearchRun / ExperimentRun
 ├─ AnalysisRun
 ├─ ClaimAssessment
 └─ Decision → derives next ResearchRun
```

所有对象不可原地覆盖。新版本保存 `supersedes`、生成原因、输入对象版本和当时可见数据集合。

### 6.2 application 层用 case 替代单一 Engine switch

建议拆成：

- `ScopeResearchQuestion`
- `BuildEvidenceMap`
- `GenerateHypothesisSet`
- `DraftAndFreezeProtocol`
- `ReproduceBaseline`
- `RunExploration`
- `FreezeCandidate`
- `RunConfirmation`
- `ExecuteAnalysisPlan`
- `AssessClaims`
- `ConductReview`
- `DecideNextAction`

`WorkflowCoordinator` 只处理合法状态转换、预算和恢复，不生成科研内容。每个 use case 使用 port 并可单独测试。

### 6.3 统一 A、B、C 与主流程

- evidence tools 的输出直接进入 EvidenceMap，不再只作为模型可选工具。
- memory 只通过显式 `MemorySnapshot` 进入某个阶段，记录采用、拒绝和冲突原因。
- bounded experiment search 必须由 frozen protocol 创建，搜索结束将完整 graph 交给 CandidateFreeze。
- 统计分析、claim gate 和 report 读取相同对象 ID，避免在自由文本中重复解释事实。

### 6.4 Skills 从 prompt 片段升级为能力契约

每个 skill 建立 manifest：

```text
name, version/hash, supportedUseCases,
inputSchema, outputSchema, tools, sideEffects,
requiredEvidence, budget, failureSemantics
```

- method skill 产出结构化 checklist/critique，不直接获得执行权限。
- script skill 经 adapter 执行，保存命令、输入 hash、输出和退出状态。
- skill 的建议必须转换为 domain 对象并通过 validator，不能只把 SKILL.md 截断后拼入 prompt。
- 同一阶段只加载满足触发条件的少量 skill，记录为什么选择和为什么未选择其他能力。

### 6.5 模型角色与独立性

- researcher：提出问题、证据综合、假设和解释；
- methodologist：只审查设计；
- statistician：只读取 protocol 和 observation，不能修改实验；
- reviewer：只读所有冻结产物，不能访问 researcher 的隐式推理；
- writer：只读取 verified claims。

角色可以使用同一底层模型，但必须有独立 session、工具权限、输入快照和预算。若研究和审查使用同一模型，报告明确标记 `model_independence=none`，不能宣称独立复核。

## 8. 验收指标

### 8.1 科研严谨性

- frozen protocol 前后对象和可见数据边界完整率：100%。
- confirmation/test 提前访问：0 次。
- 未声明 outcome 被写成 confirmatory：0 次。
- 最终关键 claim 的 evidence、analysis 和 scope provenance：100%。
- 失败 run、负结果和 protocol deviation 保留率：100%。
- baseline 未达到复现容差却宣称改进 published baseline：0 次。
- 错误实验单位、静默删 seed、方向写反和多重比较 fixture 检出率：100%。

### 8.2 研究质量

- 每个验收任务至少包含 target、null/保守解释和一个 rival。
- 每个 active hypothesis 至少有一个判别性 prediction 或被标记为不可检验。
- primary outcome 报告效应量与区间，不能只报告均值或 p-value。
- 至少一次结果导致 hypothesis weakening、redesign 或有理由停止，避免只验收成功路径。
- 人工审阅者能从结构化记录复原所有主要决策，不依赖聊天记录。

### 8.3 工程质量

- 每个 use case 可独立重放且具备幂等边界。
- migration 覆盖空库、v1.1 数据副本和失败恢复。
- 旧 v1.1 run 保持只读可查看；旧 CLI 给予迁移提示。
- 模型、检索、skill、统计和实验调用统一记录版本、输入 hash、预算和结果。
- 中断恢复不会重复 confirmation 或丢失 protocol freeze。

### 8.4 价值评估

v1.2 不以“产生正结果”验收。需要和 v1.1 对照测量：

- 研究者发现设计问题所需时间；
- 被门禁提前发现的泄漏、混杂和分析错误；
- 结果出现后发生的未登记方案修改次数；
- 最终 claim 被独立审阅者判定为过度表述的比例；
- 完成一个有界研究问题的模型调用、墙钟时间和人工审阅时间。

如果严谨性提高但成本不可接受，应优化角色、上下文和工具调用；不能删除 protocol 或 confirmation 边界换取速度。

## 9. 测试策略

- **golden research records**：正结果、负结果、inconclusive、baseline 复现失败各一套。
- **adversarial fixtures**：引用不支持主张、结果后换指标、删失败 seed、test 泄漏、HARKing、数据版本漂移。
- **statistical oracle**：与固定 R/Python 参考输出比较 effect、interval、missingness 和 multiplicity。
- **state property tests**：冻结对象不可改、任何回退产生新版本、confirmation 只执行一次。
- **human evaluation**：研究者与独立审阅者盲评 v1.1/v1.2 报告的可追溯性、结论边界和错误发现率。
- **real low-cost case**：包含 baseline 复现、至少三种假设、探索、冻结、确认和一次失败或负结果。

## 10. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 流程过重，简单任务成本过高 | 提供 `smoke`、`exploratory`、`confirmatory` profile；claim 强度随 profile 受限 |
| LLM 生成形式完整但内容空洞的 protocol | domain validator + methodologist review + 人工 protocol approval |
| 多角色只是同一模型自我认同 | 独立输入快照、权限和审查 rubric；明确报告模型独立性 |
| 统计模块试图覆盖所有学科 | v1.2 只正式支持 paired repeated-run 与 `training seed × corruption group` 分层配对，其他设计需 adapter |
| 自动探索放大选择偏差 | exploration/confirmation 硬隔离、完整搜索树、candidate freeze |
| 研究图和版本对象使迁移复杂 | append-only 新表、兼容读取、逐 use case 切换，不一次重写全部存储 |
| 过度依赖流程导致错误安全感 | 报告未验证 profile、coverage gap、模型局限和人工责任 |

## 11. 建议优先级

必须先做：

1. ResearchQuestion、HypothesisSet、ResearchProtocol 和版本冻结。
2. exploratory/confirmatory 数据边界与 CandidateFreeze。
3. ObservationTable 和确定性统计分析。
4. claim assessment、protocol deviation 和可退回决策。
5. 将 bounded search 接入主工作流。

随后做：

1. EvidenceMap 和 closest-work comparison 的质量评测。
2. skill capability manifest 和结构化调用。
3. 多维 reviewer 与独立性报告。
4. memory 的适用范围、失效条件和 adoption log。

暂缓：

- 多 agent 自由讨论；
- 自动论文全文写作；
- 大规模向量数据库和分布式执行；
- 更多领域 adapter；
- 无人工门的长时间自治。

## 12. 固定运行 profile 与资源墙

### 12.1 Profile 语义

| Profile | 用途 | 必需阶段 | 最高 claim 等级 |
| --- | --- | --- | --- |
| `smoke` | CLI、adapter、模型和实验连通性检查 | 兼容 v1.1 线性流程 | `observed`，只能称工程观察 |
| `exploratory` | 问题形成、pilot、debug和候选探索 | scope、evidence、hypothesis、protocol、exploration | `suggestive` |
| `confirmatory` | 正式 AI/ML 计算研究 | 全流程与四个人工门 | 由 confirmation、审查和复现范围决定 |

新建研究任务默认 `confirmatory`。降级 profile 必须由用户显式选择，报告首页显示 profile 和 claim 上限。profile 不能在同一 run 中升级；需要派生新 run 并重新冻结 protocol。

### 12.2 默认资源边界

真实验收任务硬上限：

| 资源 | 硬上限 |
| --- | ---: |
| GPU | 1张 |
| GPU 时间 | 12 GPU-hours |
| 总墙钟 | 24 h |
| 新增磁盘 | 20 GiB |
| 模型调用 | 20次 |
| 已知模型费用 | 10 USD |
| 并发实验 | 1 |
| confirmation执行 | 每个 frozen candidate 1次 |

这些值全部进入配置 schema，可在 brief 中调低。提高上限需要新的预算审批事件。价格未知时费用为 `unknown`，同时使用请求数、token、墙钟和 GPU 时间硬限制，不能按0美元处理。

磁盘额度包含数据副本、checkpoint、日志和临时 workspace；公共只读 cache 单独计量但必须报告。达到软阈值时停止创建大产物并清理可重建 cache；达到硬上限时保存已完成事实并停止新任务。

### 12.3 模型与人工门

- scope、protocol、candidate freeze、final claim 四个门不可关闭。
- 一次 protocol approval 可授权预算内的一组 exploration 节点，不逐实验确认。
- 最终真实案例必须使用 pi 的实际 provider/model；模型由运行配置选择，不写死在研究逻辑。
- 自动测试、故障注入和 golden fixture 可以使用确定性 model adapter。
- 不同 reviewer model 是可选增强。同一模型必须独立 session、只读权限和冻结输入，并如实报告独立性为 `none`。
- 任何模型输出先经过 schema、domain invariant 和事实门禁，不能直接改变冻结对象或数值结果。

## 13. 方法依据

本方案采用科学方法与批判性评估中的通用原则：可证伪性、竞争解释、预先声明、实验单位与混杂控制、效应量和不确定性、探索与确认分离、负结果保留、独立复现以及与证据强度相称的结论。方案形成时参考了项目已登记的 `scientific-critical-thinking` 方法 skill；该方法只用于设计审查框架，不构成本项目功能已经实现的证据。

```text
  capability_manifests, skill_invocations, model_role_sessions,
  sandbox_runs, budget_snapshots
```

所有冻结对象保存 canonical JSON hash。多表转换在事务内完成；实验、模型或统计外部调用完成后先登记不可变 result，再在短事务中推进状态。

## 16. v1.2 真实验收案例

### 16.1 用户输入

用户只提供方向和硬约束，不提供具体方法或预期正结果：

> 在单 GPU 和有限时间内，研究小型图像分类模型面对常见分布偏移时的鲁棒性或校准问题。使用公开材料和 CIFAR-10/CIFAR-10-C；不得扩大数据源、算力或访问 confirmation 数据。

Agent 必须先检索证据并提出3个候选研究问题。用户只负责选择问题和通过四个人工门，不替 agent 编写 hypothesis、protocol、candidate 或 analysis。

### 16.2 固定研究平台

- 数据：固定版本和 SHA-256 的 CIFAR-10 与 CIFAR-10-C。
- baseline suite：固定、可复现的轻量图像分类实现，至少包含一个公开常用架构；精确 revision 在 G 阶段兼容性 spike 后写入案例 manifest。
- 训练资源：单张 GPU，禁止数据并行和隐藏远程训练。
- exploration：只挂载训练、validation 和预声明的 exploration corruption roles。
- confirmation：官方 clean test 与保留 corruption groups 通过 capability 隔离，CandidateFreeze 前路径不可见。
- primary outcome：agent 在 scope/protocol 阶段从批准目录选择一个；目录至少包含 clean accuracy、mean corruption accuracy、worst-group corruption accuracy 和 calibration error。
- secondary/exploratory outcome：必须在 protocol 中预先登记。

CIFAR-10-C corruption 类型和 severity 如何划分为 exploration 与 confirmation，由 G 阶段在任何候选实验前用固定种子或静态 manifest 决定并提交 hash。划分规则一旦发布不得按结果修改。

### 16.3 真实模型要求

- 问题形成、证据综合、竞争假设、protocol 起草、结果解释和 review 必须通过 pi 使用实际配置模型。
- 统计数值、数据划分、指标、资源计量和门禁由确定性代码计算。
- 总模型调用不超过20次，总已知费用不超过10 USD。
- 保存 provider、model ID、模型配置、usage、阶段、输入 hash、输出、tool 调用和失败。
- 若模型失败或额度耗尽，run 可恢复；不得用预写 audit output 替代并登记通过。

### 16.4 验收终态

以下任一科学终态均有效：

- `publish_bounded_result`：证据支持范围受限的结果；
- `stop_inconclusive`：区间或证据无法区分竞争假设；
- `stop_low_value`：预期收益不足以支持继续投入；
- `debug_reproduction`：baseline 未复现，无法合法进入方法比较；
- `redesign`：发现设计无法判别假设，需要派生新 run。

版本验收只要求终态有充分理由和完整证据链，不要求候选优于 baseline。至少一个失败、负结果或 weakened hypothesis 必须保留在研究图中。

## 17. Bubblewrap 与本地执行边界

Docker 权限不是 v1.2 前提。执行后端按代码信任等级选择：

### 17.1 Trusted process

只允许满足全部条件的脚本：

- 路径在批准 allowlist；
- 内容 hash 与 frozen protocol 一致；
- 命令参数数组和环境变量经过 schema 校验；
- 不包含 agent 在当前 run 生成的修改；
- 使用 timeout、输出上限、进程组回收、GPU选择和资源计量。

### 17.2 Bubblewrap

任何 agent 生成或修改的代码必须在 bubblewrap 中运行，至少满足：

- `--unshare-net`，无网络 namespace；
- 项目源代码、数据和共享 cache 只读挂载；
- 仅独立 workspace、日志和声明的 artifact 目录可写；
- 不挂载 home、SSH、云配置、pi auth、`.env` 和其他 secret 路径；
- 清理环境后只注入 allowlist 变量；secret-like名称默认拒绝；
- `prlimit` 或等效机制限制进程、文件、地址空间和CPU时间；
- GPU设备只暴露批准的一张卡，记录选择和使用时间；
- 超时或崩溃后终止整个进程组并检查残留进程；
- 产物离开沙箱前验证路径、大小、媒体类型和 hash。

若本机内核或驱动使某项隔离无法实现，必须记录为具体 profile 限制并采取等价控制；不能静默回退到无限制 shell。

## 18. Migration、兼容与回滚

- v1.1 数据库升级前使用 SQLite backup API，并快照 artifact manifest。
- migration 003–006 均为不可变文件；每个文件有空库、v1.1副本、上一阶段数据库和中途失败测试。
- v1.1 `ResearchRun` 保持只读，旧 `status` 与报告路径继续可用。
- 可确定映射的 Source、Passage、Claim、ExperimentResult 可被新 run 引用；旧 hypothesis、plan 和 test 使用情况不能自动升级为 frozen/confirmatory。
- 新程序遇到高于支持版本的数据库时拒绝启动。
- 回滚只回滚程序和 active schema pointer，不删除已经写入的新对象；必要时从阶段前 backup 恢复副本。
- 每个阶段 release report 给出 migrate、verify、restore 命令和抽样结果。

## 19. Luna 执行规则

后续执行模型必须遵守：

1. 先读取项目根 README、[文档导航](../README.md)、本规划、v1.1最终报告和当前 Git 状态。
2. 每次只实施当前阶段；前一阶段tag和退出条件是硬前置。
3. 先写 ADR、domain schema、migration 和 contract test，再接模型、检索、统计或执行后端。
4. 不通过在 `details` 或自由文本中塞字段绕过正式 schema。
5. domain/application 不导入 pi、SQLite、Python、bubblewrap或数据集 SDK。
6. 冻结、数据可见性、审批和预算规则使用确定性代码，不依赖 prompt 自律。
7. 不把模拟、参数检查或 deterministic model fixture 登记成真实集成验收。
8. 发现计划假设不成立时，先写 ADR 和兼容性证据；不得降低泄漏、统计、证据或事实门禁。
9. 每阶段过程同步写入 `docs/reports/stages/v1.2-progress.md`，完成后写独立 release report。
10. 每个 release commit 前运行全量门禁、secret扫描、依赖审计、文档链接检查，并保持工作区干净。
11. 阶段 tag 使用第7节确定的版本；不得提前创建 `v1.2.0`。
12. 只有 H 阶段真实LLM案例和最终验收全部通过，才能发布 `v1.2.0`。
